## 1. 배경

현재 프론트 구현에서 개발 환경 기준의 정보(`백엔드`, `API 주소`, `localhost`, 내부 상태명 등)가 사용자 화면에 직접 노출되는 문제가 확인되었다.

실서비스 기준에서 메시지는 다음을 만족해야 한다.

1. 기술 상태가 아니라 사용자 상황을 설명해야 한다.
2. 사용자가 바로 취할 행동을 함께 제시해야 한다.
3. 입력 오류, 네트워크 오류, 세션 만료, 동기화 충돌을 서로 다른 레벨의 피드백으로 구분해야 한다.
4. 성공 안내는 흐름을 막지 않고, 실패 안내는 필요한 수준에서만 사용자를 멈춰야 한다.

## 2. 메시지 노출 계층

### 2.1 필드 인라인 에러
- 사용 위치: 폼 입력값 자체가 잘못된 경우
- 대상 예시:
  - 이메일 형식 오류
  - 비밀번호 길이 오류
  - 표시 이름 누락/길이 초과
- 노출 위치: 해당 입력 필드 바로 아래
- 원칙:
  - 한 문장으로 짧게 작성
  - 사용자가 무엇을 고쳐야 하는지 직접 설명
  - `aria-describedby`로 필드와 연결

### 2.2 폼 상단 인라인 알림
- 사용 위치: 제출은 되었지만 특정 필드 하나로 매핑하기 어려운 인증 실패
- 대상 예시:
  - 로그인 실패
  - 회원가입 중 일반 오류
  - Auth rate limit
  - Auth 네트워크 실패
- 노출 위치: CTA 버튼 위 또는 폼 액션 영역 바로 위
- 원칙:
  - 입력 흐름을 유지한다.
  - 전체 화면 에러 카드로 승격하지 않는다.
  - 같은 화면에서 다시 시도 가능해야 한다.

### 2.3 섹션 인라인 알림
- 사용 위치: 설정, 동기화, 로그아웃처럼 특정 섹션 안에서 발생한 오류
- 대상 예시:
  - 로그아웃 실패
  - 동기화 실패
  - 설정 저장 실패
- 노출 위치: 해당 섹션 내부 CTA 주변
- 원칙:
  - 문제와 해결 행동을 같이 제시
  - 섹션 맥락을 벗어나지 않음

### 2.4 차단형 레이어 / 모달
- 사용 위치: 사용자가 다음 단계로 진행하기 전에 반드시 인지해야 하는 상태
- 대상 예시:
  - bootstrap 동기화 로딩
  - bootstrap 네트워크 실패
  - bootstrap 충돌
  - 세션 만료 후 재로그인 유도
- 원칙:
  - 제목 -> 설명 -> CTA 순서를 명확히 제공
  - 배경과 시각적으로 충분히 분리
  - 스크린리더에 순서대로 전달

### 2.5 토스트
- 사용 위치: 읽고 지나가면 되는 짧은 성공/경고 피드백
- 대상 예시:
  - 설정 저장 완료
  - 수동 동기화 성공
  - 자동 포기 결과 안내
  - 로그아웃 완료
- 원칙:
  - 화면 흐름을 막지 않는다.
  - 3.5~4초 노출 후 자동 사라짐
  - 동시에 1개만 유지

### 2.6 전면 에러 화면
- 사용 위치: 해당 화면 전체가 성립하지 않을 때만 제한적으로 사용
- 금지 예시:
  - 로그인 제출 실패
  - 로그아웃 실패
  - 단순 네트워크 재시도 가능 상태
- 원칙:
  - 국소 문제를 전체 화면 실패로 확대하지 않는다.

## 3. 카피 작성 원칙

### 3.1 금지 표현
다음 표현은 사용자 UI에서 직접 노출하지 않는다.

- `백엔드`
- `API`
- `localhost`
- `응답 형식`
- `refresh token`
- `csrf`
- `401`, `403`, `429` 같은 상태 코드
- `placeholder`, `read only`, `skeleton`, `SCR-09` 같은 내부 설계 용어

### 3.2 문장 구조 원칙
- 첫 문장: 지금 무슨 일이 생겼는지 설명
- 두 번째 문장: 사용자가 지금 무엇을 해야 하는지 안내
- 최대 2문장 유지
- 기술 원인보다 사용자 행동 우선

### 3.3 톤 원칙
- 한국어 우선
- 지나치게 기계적이지 않게, 그러나 과장 없이 간결하게
- 사용자 탓처럼 쓰지 않음
- 예시:
  - 지양: `잘못 입력했습니다`
  - 권장: `입력한 내용을 다시 확인해 주세요`

### 3.4 CTA 원칙
버튼 문구는 짧은 행동형으로 통일한다.

- `다시 시도`
- `다시 로그인`
- `계속하기`
- `최신 상태 반영 후 계속`
- `대시보드로 이동`

## 4. 시나리오별 노출 방식 및 메시지

### 4.1 Auth 입력 오류
- 방식: 필드 인라인 에러
- 메시지 예시:
  - `올바른 이메일 형식을 입력해 주세요.`
  - `비밀번호는 8자 이상이어야 합니다.`
  - `표시 이름을 입력해 주세요.`

### 4.2 로그인 실패
- 방식: 폼 상단 인라인 알림
- 메시지:
  - `이메일 또는 비밀번호를 다시 확인해 주세요.`
- 비고:
  - 토스트 사용 금지
  - 전면 에러 카드 사용 금지

### 4.3 회원가입 일반 실패
- 방식: 폼 상단 인라인 알림
- 메시지:
  - `입력한 정보를 다시 확인해 주세요.`

### 4.4 Auth rate limit
- 방식: 폼 상단 인라인 알림
- 메시지:
  - `요청이 너무 많습니다. 잠시 후 다시 시도해 주세요.`

### 4.5 Auth 네트워크 실패
- 방식: 폼 상단 인라인 알림
- 메시지:
  - `지금은 연결이 원활하지 않아요. 잠시 후 다시 시도해 주세요.`
- 보조 문구 선택형:
  - `문제가 계속되면 네트워크 상태를 확인해 주세요.`

### 4.6 로그인/회원가입 성공
- 방식: 짧은 성공 상태 또는 다음 단계 이동
- 메시지:
  - `로그인이 완료됐어요.`
  - `회원가입이 완료됐어요.`
- 원칙:
  - 성공 자체보다 다음 흐름 연결이 중요
  - bootstrap이 이어질 경우 즉시 `SCR-09-A`로 전환

### 4.7 bootstrap 진행
- 방식: 차단형 로딩 레이어
- 제목:
  - `기록을 불러오고 있어요`
- 본문:
  - `잠시만 기다려 주세요.`

### 4.8 bootstrap 네트워크 실패
- 방식: 차단형 오류 레이어
- 제목:
  - `지금은 기록을 불러오지 못했어요`
- 본문:
  - `현재 기기의 기록은 그대로 유지됩니다. 잠시 후 다시 시도해 주세요.`
- CTA:
  - `다시 시도`

### 4.9 bootstrap 충돌
- 방식: 차단형 오류 레이어
- 제목:
  - `다른 기기에서 변경된 내용이 있어요`
- 본문:
  - `최신 상태를 반영한 뒤 계속 진행합니다.`
- CTA:
  - `최신 상태 반영 후 계속`

### 4.10 세션 만료 / silent refresh 실패
- 방식: 차단형 안내 또는 로그인 화면 상단 배너
- 제목:
  - `로그인이 만료되었어요`
- 본문:
  - `다시 로그인해 주세요. 이 기기의 기록은 그대로 유지됩니다.`
- CTA:
  - `다시 로그인`

### 4.11 로그아웃 실패
- 방식: 설정 화면 세션 관리 섹션 인라인 알림
- 메시지:
  - `지금은 로그아웃이 어렵습니다. 잠시 후 다시 시도해 주세요.`

### 4.12 로그아웃 성공
- 방식: 토스트 또는 즉시 화면 이동
- 메시지:
  - `안전하게 로그아웃되었어요.`
- 원칙:
  - 즉시 로그인 화면으로 이동한다면 토스트는 선택 사항

### 4.13 설정 저장 성공
- 방식: success toast
- 메시지:
  - `설정이 저장되었어요.`

### 4.14 수동 동기화 성공
- 방식: success toast
- 메시지:
  - `최신 상태로 동기화되었어요.`

### 4.15 동기화 네트워크 실패
- 방식: 설정 화면 인라인 알림
- 메시지:
  - `지금은 동기화가 어렵습니다. 잠시 후 다시 시도해 주세요.`
- 보조 문구:
  - `현재 기록은 이 기기에 안전하게 보관됩니다.`
- CTA:
  - `다시 시도`

### 4.16 동기화 충돌
- 방식: 설정 화면 인라인 alert 우선
- 메시지:
  - `다른 기기에서 변경된 내용이 있어요.`
  - `최신 상태를 반영한 뒤 계속할 수 있습니다.`
- CTA:
  - `최신 상태 반영`

## 5. 접근성 규칙

- 필드 에러는 반드시 `aria-describedby`로 연결한다.
- 인라인 알림은 `role="alert"` 또는 `aria-live="polite"`를 사용한다.
- 차단형 레이어는 제목, 본문, CTA가 읽는 순서대로 DOM에 배치되어야 한다.
- 토스트는 스크린리더용 상태 텍스트를 포함한다.
- 같은 오류가 반복될 때 불필요한 깜빡임 없이 메시지를 갱신한다.

## 6. FE 적용 가이드

### 6.1 Auth 화면
- 로그인 실패, rate limit, 네트워크 실패는 전면 `ErrorState` 대신 폼 상단 인라인 알림으로 통일한다.
- 필드 오류와 일반 알림은 시각적으로 구분하되, 카드 안에서 해결 가능해야 한다.
- 성공 상태는 오래 머무는 카드보다 다음 흐름 전환을 우선한다.

### 6.2 bootstrap 레이어
- 성공 직후 바로 대시보드 이동 금지
- `SCR-09-A` 레이어에서 로딩/오류/충돌을 분기
- 네트워크 실패와 충돌은 서로 다른 CTA를 가져야 한다.

### 6.3 설정 화면
- 로그아웃 실패는 세션 관리 섹션 안에서 처리한다.
- 설정 저장/수동 동기화 성공은 toast로 짧게 노출한다.
- 충돌/네트워크 실패는 섹션 인라인 alert 우선

### 6.4 공통 네트워크 오류
- 개발용 주소, 인프라 용어, 상태코드를 직접 노출하지 않는다.
- 공통 기본 문구는 아래를 사용한다.
  - `지금은 연결이 원활하지 않아요. 잠시 후 다시 시도해 주세요.`

## 7. 우선 반영 순서

1. Auth 화면: 전면 에러 제거, 폼 상단 인라인 알림 통일
2. silent refresh 실패 시 로그인 만료 배너/레이어 추가
3. bootstrap 레이어 문구 확정
4. 설정 화면 success toast / sync alert 정식 도입
5. 공통 메시지 컴포넌트 또는 메시지 사전 분리

## 8. 아카이브 메모

- 이 문서는 `ui_text_definition.md`의 세부 상태를 실서비스용 메시지 체계로 구체화하기 위해 작성된 병합 전 설계안이다.
- 현재 구현과 검수의 단일 정본은 `ui_text_definition.md`이며, 이 문서는 변경 이력 추적과 초기 의도 확인 용도로만 참조한다.
- FE/QA/UI-RV는 새 판단 기준을 추가로 만들지 않고 `ui_text_definition.md`를 우선 참조한다.
