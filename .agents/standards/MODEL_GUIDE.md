# 모델별 성능 및 워크플로우 매핑 가이드 (MODEL_GUIDE)

이 문서는 Antigravity 시스템에서 현재 사용 중인 AI 에이전트 모델인 **Gemini**, **Claude Code (Opus, Sonnet)**, **Codex**를 프로젝트 라이프사이클에 맞게 선택하기 위한 표준 가이드입니다.

세부 버전명은 제품 업데이트에 따라 바뀔 수 있으므로, 이 문서는 **고정 버전명보다 모델 계열의 역할과 강점**을 기준으로 해석합니다.

---

## 1. 모델 포트폴리오와 기본 역할

업무 성격에 따라 모델을 아래처럼 배치합니다.

| 역할 티어 | 모델 | 핵심 강점 | 대표 활용 |
| :--- | :--- | :--- | :--- |
| **Architect** | **Gemini** | 대규모 컨텍스트 처리, 멀티모달 입력, 초안 구조화 | PRD 해석, 기능/정책 구조화, 설계 초안 |
| **Specialist** | **Claude Code Opus** | 깊은 추론, 복잡한 트레이드오프 판단, 리스크 탐지 | 아키텍처 결정, 난제 분석, 고위험 정책 검토 |
| **Builder** | **Codex** | 실제 저장소 탐색, 코드 수정, 터미널 기반 실행-검증 루프 | 구현, 리팩터링, 테스트 작성/수정, 빠른 유지보수 |
| **Reviewer** | **Claude Code Sonnet** | 논리 정합성, 코드 리뷰, 시나리오 기반 검수 | 코드 리뷰, QA, 버그 재현 분석, 요구사항 대조 |

### 핵심 해석

- **Gemini**는 넓은 문맥을 빠르게 읽고 구조를 잡는 데 강합니다.
- **Claude Code Opus**는 애매하거나 비용이 큰 결정을 내릴 때 가장 신뢰할 수 있는 심층 추론 모델입니다.
- **Codex**는 실제 워크스페이스 안에서 파일을 읽고 수정하며 검증하는 **실행 중심 모델**로 봅니다.
- **Claude Code Sonnet**은 구현 이후의 검수, 논리 점검, 테스트 시나리오 정제에 가장 적합합니다.

## 2. 모델별 상세 활용 원칙

### 2.1 Gemini: 대규모 문맥 설계자

Gemini는 문서량이 많고 여러 소스의 정보를 한 번에 읽어야 하는 작업에 우선 배치합니다.

- **PRD / 정책 / 요구사항 압축**: 긴 기획 문서, 다수의 참조 문서를 빠르게 요약하고 핵심 쟁점을 구조화
- **초안 설계**: 화면 흐름, 도메인 개념도, API 범위, 작업 분해 초안 작성
- **멀티모달 설계 보조**: UI 레퍼런스 이미지나 시각 자료를 함께 보고 방향 정리

다만 아래 상황에서는 Gemini 단독 확정 대신 다른 모델로 핸드오프합니다.

- 결제, 권한, 정산, 보안처럼 **실수 비용이 큰 정책**
- 복잡한 트레이드오프가 얽힌 구조 변경
- 구현 직전의 구체적인 코드 수정과 검증

### 2.2 Claude Code Opus: 고위험 의사결정 담당

Opus는 다음과 같이 **"생각을 오래 해야 하는 문제"**에 사용합니다.

- **Critical Decision**: 프레임워크 변경, 데이터 모델 재설계, 인프라 전환
- **Ambiguous Requirement**: 요구사항이 모호하거나 서로 충돌하는 상황
- **Complex Logic**: 정산, 랭킹, 상태 전이, 권한, 예외 규칙이 많은 도메인 로직
- **Deep Refactoring Strategy**: 레거시 개선 전략, 부채 상환 순서, 마이그레이션 방안 수립

Opus의 결과물은 바로 구현으로 넘기기보다, **결정 사유와 제외한 대안까지 정리한 설계 판단서**로 남기는 것이 좋습니다.

### 2.3 Codex: 저장소 기반 실행자

Codex는 실제 코드베이스 안에서 가장 높은 생산성을 내는 모델입니다.

- **구현 작업**: 기능 추가, 버그 수정, 리팩터링, 테스트 추가
- **저장소 탐색**: 관련 파일과 호출 흐름을 찾고 영향 범위를 파악
- **검증 루프**: 테스트 실행, 린트 확인, 실패 원인 추적, 재수정
- **작은 범위의 반복 작업**: 문서/코드 동기화, 타입 오류 수정, 스캐폴딩, 어댑터 작성

Codex는 특히 아래 조건에서 우선 배치합니다.

- 작업 대상 파일과 수정 범위가 비교적 명확함
- 실제 코드 변경과 검증이 필요함
- "설명"보다 "완료된 패치"가 중요한 단계임

반대로 아래 경우에는 Gemini나 Opus 선행이 더 낫습니다.

- 아직 문제 정의가 흐릿함
- 여러 도메인의 정책 충돌을 먼저 정리해야 함
- 창의적 컨셉 기획이나 제품 방향성 정리가 먼저 필요함

### 2.4 Claude Code Sonnet: 정밀 검수자

Sonnet은 구현 이후 품질을 단단하게 만드는 역할로 사용합니다.

- **Code Review**: 요구사항 대비 누락/과잉 구현 여부 확인
- **Edge Case Inspection**: 비정상 입력, 경계값, 예외 흐름 검토
- **QA 시나리오 설계**: 테스트 케이스, 재현 절차, 회귀 체크리스트 정리
- **Spec vs Code 검증**: PRD, 설계서, 실제 코드의 정합성 비교

Sonnet은 직접 구현도 가능하지만, 이 가이드에서는 **"작성자"보다 "검수자" 역할**에 우선 배치합니다.

## 3. 권장 협업 패턴

모델은 경쟁적으로 쓰기보다, 단계별로 역할을 나눠 연결할 때 가장 효율적입니다.

### 3.1 기본 패턴: Wide -> Deep -> Build -> Review

1. **Gemini**
   요구사항과 참조 문서를 넓게 읽고 초안을 구조화합니다.
2. **Claude Code Opus**
   비용이 큰 기술적/정책적 판단을 확정합니다.
3. **Codex**
   저장소에서 실제 코드를 수정하고 검증합니다.
4. **Claude Code Sonnet**
   구현 결과를 요구사항과 대조하며 검수합니다.

### 3.2 빠른 실행 패턴: Build -> Review

명확한 버그 수정이나 범위가 작은 기능 추가는 아래처럼 단축합니다.

1. **Codex**로 바로 구현
2. **Claude Code Sonnet**으로 리뷰 및 QA

### 3.3 고위험 패턴: Wide -> Deep -> Review -> Build -> Review

결제, 보안, 데이터 마이그레이션처럼 실수 비용이 큰 경우:

1. **Gemini**로 문맥 정리
2. **Claude Code Opus**로 설계 판단
3. **Claude Code Sonnet**으로 설계 초안 자체를 한 번 더 점검
4. **Codex**로 구현
5. **Claude Code Sonnet**으로 최종 검수

## 4. 워크플로우 매핑 매트릭스

에이전트 명령어 수행 시 아래 기준으로 모델을 배치합니다.

| 워크플로우 | 1순위 모델 | 2순위/핸드오프 | 이유 및 활용 포인트 |
| :--- | :--- | :--- | :--- |
| **기획 (`/po-plan`)** | `Gemini` | `Claude Code Opus` | 대규모 PRD/정책 문맥을 빠르게 구조화하고, 복잡한 정책 충돌은 Opus로 확정 |
| **기획 검수 (`/po-rv`)** | `Claude Code Sonnet` | `Claude Code Opus` | 요구사항 누락, 논리 충돌, 예외 시나리오 점검에 적합 |
| **백엔드 설계 (`/be-plan`)** | `Gemini` | `Claude Code Opus` | API, DB, 도메인 규칙을 폭넓게 정리하고 고위험 설계 판단은 Opus 담당 |
| **프론트엔드 설계 (`/fe-plan`)** | `Gemini` | `Claude Code Sonnet` | 화면 흐름과 상태 설계를 빠르게 구조화하고, 상호작용/예외 상태 정합성은 Sonnet 검토 |
| **UI/UX 설계 (`/ui-plan`)** | `Gemini` | `Claude Code Opus` | 레퍼런스와 경험 흐름을 넓게 정리하고, 컨셉 밀도와 차별화는 Opus로 심화 |
| **DB 설계 (`/db-plan`)** | `Gemini` | `Claude Code Opus` | 엔터티/관계/제약사항을 정리하고 정규화/무결성/마이그레이션 판단은 Opus 담당 |
| **구현 (`/be-act`, `/fe-act`, `/db-act`, `/ui-act`)** | `Codex` | `Gemini` 또는 `Claude Code Sonnet` | 실제 코드 편집, 테스트, 검증 루프는 Codex가 주도하고 필요 시 문맥 보강/검수 연결 |
| **구현 검수 (`/be-rv`, `/fe-rv`, `/db-rv`, `/ui-rv`)** | `Claude Code Sonnet` | `Codex` | Sonnet이 논리/정합성 리뷰를 맡고, 수정 적용과 재검증은 Codex가 수행 |
| **QA/테스트 (`/qa`)** | `Claude Code Sonnet` | `Codex` | 테스트 시나리오 설계와 결함 탐지는 Sonnet, 자동화 코드 작성과 재현은 Codex |
| **시스템 최적화 (`/atg`)** | `Gemini` | `Codex` | 운영 원칙/사용 패턴 정리는 Gemini, 실제 저장소 기준 명령 예시 검증은 Codex |
| **빠른 유지보수** | `Codex` | `Gemini` | 작은 코드 수정, 문서 동기화, 로그 기반 수정은 Codex가 가장 효율적 |

## 5. Antigravity 운영 팁

### 5.1 설계와 구현의 역할을 분리합니다

- 설계 초안은 **Gemini**
- 고위험 판단은 **Claude Code Opus**
- 실제 수정은 **Codex**
- 최종 검수는 **Claude Code Sonnet**

한 모델에 모든 역할을 몰아주기보다, 각 모델이 잘하는 구간만 맡기는 것이 결과 품질과 토큰 효율 모두에 유리합니다.

### 5.2 Codex에는 "문서 전체"보다 "작업 범위"를 줍니다

Codex는 저장소를 직접 읽고 수정하는 데 강하므로, 긴 설명보다 아래가 더 효과적입니다.

- 수정 대상 경로
- 기대 동작
- 실패 중인 테스트 또는 에러 메시지
- 변경 금지 범위

예시:

```text
/be-act, @[backend/src/user/] 범위에서 사용자 비활성화 API를 구현해줘.
조건은 soft delete 유지, 기존 조회 API 응답 스키마는 변경하지 말고 관련 테스트까지 갱신해줘.
```

### 5.3 Opus와 Sonnet은 "판단 근거"를 남기게 합니다

Claude 계열은 결과만 받기보다, 아래를 함께 남기게 해야 핸드오프가 안정적입니다.

- 선택한 안과 기각한 안
- 주요 리스크
- 엣지 케이스
- 후속 구현 시 주의점

### 5.4 Gemini는 컨텍스트 허브로 사용합니다

문서가 많을수록 Gemini에 먼저 아래 작업을 맡기면 이후 단계가 가벼워집니다.

- 긴 문서 요약
- 충돌하는 요구사항 정리
- 구현 전 체크리스트 생성
- 각 파트별 핸드오프 문장 작성

### 5.5 리뷰는 가능하면 작성 모델과 분리합니다

- **Codex가 구현했다면 Sonnet으로 리뷰**
- **Gemini가 설계했다면 Opus 또는 Sonnet으로 검토**
- **Opus가 결정했다면 Sonnet으로 반대 관점 점검**

동일 모델 자기검수보다, 역할이 다른 모델 간 교차 검수가 더 안정적입니다.

---

## 6. 유지 관리 원칙

- **모델 변경 시 즉시 갱신**: 실제 사용 모델 풀이 바뀌면 본 문서의 티어와 매핑을 함께 수정합니다.
- **버전보다 제품군 중심 유지**: 세부 버전이 바뀌어도 사용 원칙이 유지되도록 문장을 작성합니다.
- **프로젝트 경험 반영**: 특정 도메인에서 Codex, Sonnet, Opus가 유독 강하거나 약했던 패턴을 누적 반영합니다.
- **핸드오프 규칙 보강**: 모델 간 작업 인계가 자주 깨지는 지점은 프롬프트 예시와 함께 보완합니다.

> [!IMPORTANT]
> **핵심 선택 원칙 (Golden Rule)**  
> **"넓은 문맥 정리는 Gemini, 고난도 판단은 Claude Code Opus, 실제 구현은 Codex, 최종 검수는 Claude Code Sonnet"**
