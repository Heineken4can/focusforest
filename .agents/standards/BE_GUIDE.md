# 백엔드 스탠다드 및 가이드라인 (BE)

이 문서는 백엔드 설계, 구현, 리뷰, 핸드오프 전 과정에서 공통으로 따르는 단일 원본입니다.
`be-plan`, `be-rv`, `be-act`는 모두 이 문서를 기준으로 판단하며, 스킬 문서는 이 기준을 작업에 맞게 적용하는 보조 수단으로만 사용합니다.

---

## 0. 문서 목적과 적용 범위

- 적용 대상: `docs/04. be/`, `backend/`, 백엔드 연동에 직접 영향을 주는 설정 및 테스트 코드
- 적용 단계: 설계(`be-plan`), 리뷰(`be-rv`), 구현(`be-act`)
- 우선순위: 본 문서 > 스킬 문서 > 임시 작업 메모
- 목표: 설계 원칙, 구현 기본값, 리뷰 기준, 완료 조건을 한 문서에서 일관되게 제공

---

## 1. AI 협업 및 프로젝트 특화 원칙

- **도메인 권한 엄수**: 백엔드 에이전트는 `docs/04. be/`, `backend/`, `.agents/standards/BE_GUIDE.md` 범위에서만 직접 수정합니다.
- **크로스 도메인 읽기 전용**: FE, UI, DB, PO 문서와 코드는 읽기만 가능하며, 변경이 필요하면 백엔드 폴더 하위에 제안서를 남깁니다.
- **Architecture-First**: 코드 작성 전 시스템 구조, 모듈 경계, API 계약, 데이터 흐름을 문서로 먼저 확정합니다.
- **문서와 코드의 분리**: 설계 계약은 문서에, 구현 규칙은 이 문서에, 리뷰 출력 형식은 워크플로우/스킬에 둡니다.
- **안전한 핸드오프**: 설계에서 구현, 구현에서 리뷰로 넘어갈 때 완료 범위, 미완 항목, 리스크, 테스트 상태를 명시합니다.

---

## 2. 설계 원칙

### 2.1 계층 구조와 책임 분리

- 기본 계층은 `Controller -> Service -> Repository`를 따릅니다.
- `Controller`는 요청/응답, 인증된 사용자 컨텍스트 해석, 입력 검증만 담당합니다.
- `Service`는 순수 비즈니스 규칙, 상태 전이, 트랜잭션 경계를 담당합니다.
- `Repository`는 데이터 저장소 접근과 쿼리 최적화만 담당합니다.
- 컨트롤러에 도메인 로직, 레포지토리에 정책 판단을 넣지 않습니다.

### 2.2 모듈 경계와 의존성 방향

- 모듈 간 의존성은 단방향으로 유지합니다.
- 다른 도메인의 구체 구현에 직접 의존하지 말고 공개 계약 또는 인터페이스를 통해 연결합니다.
- `Common` 계층은 범용 기능만 포함하며 특정 도메인에 의존하지 않습니다.
- 순환 참조가 필요한 구조는 설계가 잘못된 것으로 간주하고 먼저 분리 방안을 찾습니다.

### 2.3 API 및 시스템 아키텍처 원칙

- RESTful 설계를 기본으로 하되, 중요한 것은 URI 취향보다 계약의 일관성입니다.
- 모든 외부 API는 요청/응답 스키마, 인증 방식, 에러 코드, rate limit 여부를 문서화합니다.
- API 버전은 URI 또는 명시적 버전 전략으로 일관되게 관리합니다.
- 구조적으로 중요한 설정은 앱 시작 시점에 fail-fast 검증을 수행합니다.

## 3. 구현 컨벤션

### 3.1 파일/폴더 배치 규칙

- 모듈 단위 디렉터리를 기본으로 하고, 모듈 내부에서 `controller`, `service`, `dto`, `repository`, `entities`를 분리합니다.
- 테스트는 구현 코드와 가까운 위치에 두되, e2e는 별도 테스트 디렉터리에 둡니다.
- 공통 유틸은 `common/`에 두고, 특정 도메인 로직을 재사용 가능한 유틸로 위장해 넣지 않습니다.

### 3.2 네이밍 규칙

- 클래스는 `PascalCase`, 메서드와 변수는 `camelCase`, 상수는 `UPPER_SNAKE_CASE`를 사용합니다.
- boolean 값은 `is`, `has`, `should`, `can` 접두어를 붙입니다.
- DTO는 요청과 응답을 역할별로 분리하고 이름에 목적을 드러냅니다.
- 모호한 이름(`data`, `result`, `temp`)은 금지하고 도메인 의미를 드러냅니다.

### 3.3 Controller / Service / Repository 작성 규칙

- Controller는 DTO 검증과 HTTP 상태 코드 결정을 담당하되, 정책 분기는 Service로 넘깁니다.
- Service는 비즈니스 시나리오 단위로 작게 분리하고, 조기 반환으로 분기 중첩을 낮춥니다.
- Repository는 조회 목적에 맞는 `select` 또는 projection을 사용하고 전체 컬럼 조회를 기본값으로 두지 않습니다.
- 다른 서비스가 꼭 필요하면 직접 `new`로 생성하지 말고 DI를 사용합니다.

### 3.4 DTO / 응답 타입 규칙

- 모든 외부 입력은 DTO 또는 schema validation을 통해 검증합니다.
- 응답 타입은 문서와 코드 모두에서 명시적으로 정의합니다.
- 성공 응답의 HTTP 상태 코드는 엔드포인트 의미에 맞게 선택합니다.
  - 생성: `201`
  - 동기 조회/수정: `200`
  - 본문 없는 삭제/완료: `204`
  - 비동기 수락: `202`
- 성공 응답이라고 해서 모든 엔드포인트를 `200`으로 통일하지 않습니다.
- 공통 응답 포맷이 프로젝트에 정의되어 있다면 일관되게 사용합니다.

### 3.5 예외 처리 규칙

- 예외는 도메인 의미가 드러나는 방식으로 발생시킵니다.
- `try-catch`는 복구 가능한 경계에서만 사용하고 흐름 제어 수단으로 남발하지 않습니다.
- 글로벌 예외 필터와 충돌하는 임의의 응답 조작은 지양합니다.
- `HttpException` 자체를 금지하지는 않지만, 반복되는 비즈니스 오류는 공통 예외 전략으로 추상화하는 편을 우선합니다.

### 3.6 Config / 환경변수 규칙

- 애플리케이션 코드에서 `process.env.*` 직접 참조를 기본값으로 삼지 않습니다.
- 설정은 `ConfigService` 또는 동등한 중앙 설정 계층을 통해 읽습니다.
- 시크릿, 포트, 외부 URL, rate limit 수치 등 환경별 값은 하드코딩하지 않습니다.
- `.env.example`에 필수 키와 의미를 문서화합니다.

### 3.7 로깅 규칙

- `console.log`를 기본 로깅 수단으로 사용하지 않습니다.
- 구조화 로그를 사용하고 `timestamp`, `level`, `message`, `requestId`를 포함합니다.
- 토큰, 비밀번호, 개인정보는 마스킹 후 기록합니다.
- 정상 흐름의 디버그 로그는 운영에서 비활성화 가능해야 합니다.

### 3.8 트랜잭션 및 데이터 접근 규칙

- 여러 쓰기 작업이 하나의 비즈니스 결과를 만들어야 한다면 단일 트랜잭션 경계를 명시합니다.
- 트랜잭션 경계는 Service에 두고 Repository 내부에 숨기지 않습니다.
- 루프 안의 반복 조회, N+1, 불필요한 직렬 await는 기본적으로 문제로 봅니다.
- 캐시 사용은 읽기 빈도와 무효화 비용이 명확할 때만 도입합니다.

### 3.9 보안 구현 규칙

- 인증/인가 로직은 Controller 본문에 하드코딩하지 않고 guard, middleware, interceptor 등 경계 계층에 둡니다.
- 보호된 엔드포인트는 메서드, 컨트롤러, 글로벌 레벨 중 하나에서 유효한 가드 보호를 받아야 합니다.
- Rate limiting은 특정 데코레이터 이름이 아니라 실효성 있는 보호 여부를 기준으로 판단합니다.
- raw query 사용 시 파라미터 바인딩을 강제합니다.

## 4. 테스트 최소 기준

- 핵심 비즈니스 로직은 Service 단위 테스트를 우선 작성합니다.
- 실패하는 테스트를 먼저 작성하는 TDD를 기본값으로 권장합니다.
- 최소 검증 범위:
  - 성공 경로
  - 대표 실패 경로
  - 경계값 또는 상태 전이 예외
- Service Layer 커버리지는 80% 이상, 전체 프로젝트는 60% 이상을 목표로 합니다.
- e2e 테스트는 인증, 핵심 생성/수정/조회 흐름, 주요 에러 응답을 검증합니다.
- `expect(result).toBeDefined()` 수준의 약한 단언으로 테스트를 끝내지 않습니다.

## 5. 리뷰 체크포인트

### 5.1 정확성

- 상태 전이, 멱등성, 트랜잭션 경계, 예외 전파가 올바른가
- 페이지네이션 없는 대량 조회나 중복 생성 위험이 없는가

### 5.2 보안

- 인증/인가가 실제로 적용되는가
- DTO 검증과 입력 sanitization이 충분한가
- 민감 정보가 응답이나 로그에 노출되지 않는가

### 5.3 성능

- N+1, 직렬 await, 과도한 select, 커넥션 재생성이 없는가
- 캐시가 필요한 구간과 아닌 구간이 구분되어 있는가

### 5.4 타입 안전성

- `any`, 무분별한 type assertion, nullable 값 미처리가 없는가
- DTO와 실제 응답 타입이 일치하는가

### 5.5 테스트 가능성

- 의존성 주입이 되어 있는가
- 비즈니스 로직과 I/O가 과도하게 섞여 있지 않은가
- 핵심 분기에 테스트 공백이 없는가

### 5.6 프로젝트 관례 준수

- 폴더 구조, 네이밍, config, logger, 응답 포맷이 일관적인가
- 성공 상태 코드는 엔드포인트 의미에 맞게 선택되었는가

---

## 6. Done Criteria

- 빌드 에러와 타입 에러가 없다.
- 린트 규칙을 통과한다.
- 핵심 비즈니스 로직에 대한 테스트가 추가되거나 갱신되었다.
- 보안 관련 하드코딩과 민감 정보 노출이 없다.
- API 계약, 설정, 에러 코드 변경이 있으면 관련 문서가 함께 갱신되었다.

---

## 7. Handoff 기준

### 7.1 to BE-Review

- 변경 범위 요약
- 남은 리스크
- 테스트 실행 결과
- 확인이 필요한 설계 가정

### 7.2 to DB

- 엔터티 변경 배경
- 트랜잭션 요구사항
- 인덱스 또는 무결성 요구사항

### 7.3 to FE

- 확정된 API 요청/응답 스키마
- 에러 코드
- 인증/인가 흐름
- 비동기 완료 상태 또는 폴링 전략

---

## 8. 역할별 특별 지침

### BE-Plan

- 아키텍처, 모듈 경계, API 계약, 비기능 요구사항을 먼저 확정합니다.
- DB와 FE가 구현 가능한 수준으로 계약을 명시합니다.

### BE-Review

- 원본 문서나 코드를 직접 수정하지 않고 findings-first 리포트만 남깁니다.
- 계약 드리프트가 보이면 문서 정합성 리뷰로 에스컬레이션합니다.

### BE-Act

- 직전 설계와 리뷰 findings 범위 안에서만 수정합니다.
- 범위 확장이 필요하면 먼저 문서 또는 제안서를 갱신합니다.
