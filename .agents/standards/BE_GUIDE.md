# 백엔드 스탠다드 및 가이드라인 (BE)

이 문서는 시스템 아키텍처 및 서버 사이드 개발(BE-Plan, BE-Review, BE-Act) 시 지켜야 할 클린 코드 및 TDD 규범입니다. 더불어, 프로젝트 초기의 핵심 인프라 구상 및 기술 스택 선정에 대한 기준을 제공합니다.

---

## 0. AI 협업 및 프로젝트 특화 원칙 (Core Workflow)

실무 프로젝트 경험을 바탕으로, AI 파트너와 협업 시 아래 원칙을 최우선으로 적용합니다.

- **도메인 권한 엄수 (Cross-Domain Read-Only)**: 백엔드 에이전트(`be-plan`, `be-rv`, `be-act`)는 백엔드 전용 작업 폴더(`docs/04. be/`, `backend/` 등) 및 스탠다드 로컬 파일(`.agents/standards/BE_GUIDE.md`) 내에서만 쓰기/수정 권한을 가집니다. 기술(FE) 문서나 프론트엔드 코드, 일반 기획 문서(`PRD.md`), 디자인 문서를 수정해야 할 경우, 절대 직접 덮어쓰지 않고 `docs/04. be/` 하위에 수정 제안서 마크다운(.md) 파일(예: `docs/04. be/schema_modification_request.md`)을 작성한 뒤 유저에게 해당 파트의 에이전트를 호출하도록 가이드합니다.
- **아키텍처 선행 원칙 (Architecture-First)**: 코드를 짜기 전, 기획 산출물을 바탕으로 시스템 아키텍처 다이어그램과 데이터 흐름, 핵심 기술 스택을 완벽하게 다큐멘테이션(문서화)하여 타 파트가 참고할 수 있게끔 확정지어야 합니다.
- **안전한 핸드오프 (Handoff)**: 기획(PO)에서 내려온 요구사항을 설계(Plan)가 넘겨받고, 구현(Act)으로 이어지는 과정에서 서로의 의도가 끊기지 않도록, 각 단계 간에는 명시적인 Handoff 산출물을 전달해야 합니다.

## 1. 시스템 아키텍처 및 인프라 설계 (System Architecture & Infrastructure)
- **플랫폼 및 환경 분석**: PRD(제품 요구사항 명세서)를 기반으로 시스템이 구동될 환경(로컬, 클라우드 등)을 분석하고, 그에 맞는 최적의 기술 스택과 인프라를 선정합니다.
- **계층형 아키텍처 (Layered Architecture)**: `Controller` -> `Service` -> `Repository`의 계층 구조를 엄격히 준수합니다.
    - **Controller**: HTTP 요청/응답 처리 및 입력값 검증(Validation)만 담당합니다.
    - **Service**: 트랜잭션 관리 및 순수한 비즈니스 로직만 수행합니다.
    - **Repository**: 데이터베이스와의 통신만 담당합니다.
- **의존성 주입 (DI)**: 강결합을 피하기 위해 인터페이스를 활용한 의존성 주입 패턴을 사용하여 테스트 용이성을 극대화합니다.

---

## 2. API 설계 원칙 (RESTful)
- **URI 규칙**: 명사 및 복수형을 사용하며, 행위는 HTTP 메서드(`GET`, `POST`, `PUT`, `PATCH`, `DELETE`)로 분리합니다.
- **응답 전문 통일**: 클라이언트에게 일관된 구조(Status, Message, Data 등)로 JSON 응답을 내려주는 공통 응답 포맷을 사용합니다.
- **버저닝**: API URI에 반드시 버전을 부여하여 하위 호환성을 보장합니다. (예: `/api/v1/users`)
- **API 문서화**: Swagger(OpenAPI 3.0) 기반으로 API 명세를 자동 생성하며, 모든 엔드포인트는 요청/응답 스키마와 예제를 포함해야 합니다. API 문서는 개발 서버에서 `/api-docs` 경로로 접근 가능하도록 설정합니다.

---

## 3. 클린 코드 및 TDD (테스트 주도 개발)
- **TDD (Red-Green-Refactor)**: 핵심 비즈니스 로직(Service) 작성 시, 반드시 실패하는 테스트를 먼저 작성(Red)한 뒤 통과(Green)시키고 리팩토링(Refactor)하는 사이클을 유지합니다.
- **TDD 적용 범위 및 커버리지 목표**:
    - **필수 대상**: Service Layer의 비즈니스 로직, 유틸리티/헬퍼 함수, Custom Validator
    - **권장 대상**: Repository Layer의 복잡한 쿼리, 미들웨어/인터셉터의 핵심 분기
    - **커버리지 목표**: Service Layer 80% 이상, 전체 프로젝트 60% 이상
- **예외 처리 전략**: `try-catch`로 비즈니스 로직의 흐름을 제어하지 않고, `Custom Exception`을 던진 뒤 `Global Exception Handler`에서 일괄적으로 Catch하여 처리합니다.
- **조기 반환 (Early Return)**: 조건문의 깊이(Depth)를 줄이기 위해 예외 케이스는 메서드 상단에서 바로 `return` 하거나 `throw` 처리합니다.

## 4. 보안 (Security)
- **인증/인가 분리**: 인증(Authentication) 및 인가(Authorization) 처리를 API 로직 안으로 하드코딩하지 않고, 미들웨어나 인터셉터 구간에서 분리 처리합니다.
- **입력값 검증**: 모든 외부 입력에 대해 타입, 길이, 형식, 허용 범위를 검증합니다. 검증은 Controller 진입 시점(DTO/Schema Validation)에서 수행하며, 화이트리스트 방식을 우선 적용합니다.
- **Injection 방어**: XSS, SQL/NoSQL Injection에 대해 파라미터 바인딩 및 이스케이프 처리를 적용합니다.
- **CORS 정책**: 허용 Origin을 환경별로 명시적으로 지정하며, 와일드카드(`*`) 사용은 개발 환경에서만 허용합니다. 운영 환경에서는 허용 도메인, 메서드, 헤더를 최소 범위로 제한합니다.
- **HTTPS**: 운영/스테이징 환경에서는 HTTPS를 필수 적용하며, HTTP 요청은 HTTPS로 리다이렉트합니다.
- **Secret 및 환경변수 관리**: API 키, DB 비밀번호, JWT Secret 등 민감 정보는 절대 소스 코드에 하드코딩하지 않습니다. 환경변수 또는 Secret Manager를 통해 주입하며, `.env` 파일은 `.gitignore`에 반드시 등록합니다.
- **Rate Limiting / Throttling**: 공개 API 및 인증 관련 엔드포인트(로그인, 회원가입 등)에는 Rate Limiting을 적용하여 무차별 대입 공격(Brute Force) 및 남용을 방지합니다. 제한 기준(요청 수/시간 윈도우)은 엔드포인트 성격에 맞게 설정합니다.

## 5. 환경별 설정 관리 (Configuration Management)
- **환경 분리**: `development`, `staging`, `production` 환경을 명확히 구분하고, 각 환경별 설정을 독립적으로 관리합니다.
- **.env 분리 전략**: 환경별 `.env` 파일을 분리합니다 (예: `.env.development`, `.env.staging`, `.env.production`). 공통 설정은 `.env`에, 환경 특화 설정은 환경별 파일에 배치합니다.
- **Config 관리 기준**:
    - 환경에 따라 변하는 값(DB 호스트, API URL 등)은 반드시 환경변수로 관리합니다.
    - 환경에 무관한 상수(페이지 사이즈, 기본 타임아웃 등)는 config 파일에 정의합니다.
    - 설정값에 대한 타입 검증 및 필수값 누락 체크를 앱 시작 시점에 수행합니다 (fail-fast).
- **설정 파일 템플릿**: `.env.example` 파일을 레포지토리에 포함하여 필요한 환경변수 목록과 형식을 문서화합니다.

## 6. 로깅 및 모니터링 (Logging & Monitoring)
- **Structured Logging**: 로그는 JSON 형식의 구조화된 로깅을 적용하여 검색과 분석이 용이하도록 합니다. 최소 포함 필드: `timestamp`, `level`, `message`, `requestId`.
- **로그 레벨 기준**:
    - `ERROR`: 즉시 대응이 필요한 시스템 장애, 처리 불가능한 예외
    - `WARN`: 잠재적 문제, 비정상적이지만 서비스 지속 가능한 상황
    - `INFO`: 주요 비즈니스 이벤트 (사용자 가입, 결제 완료 등)
    - `DEBUG`: 개발/디버깅용 상세 정보 (운영 환경에서는 비활성화)
- **민감 정보 마스킹**: 로그에 비밀번호, 토큰, 개인정보 등 민감 데이터가 포함되지 않도록 마스킹 처리합니다.
- **요청 추적**: 각 요청에 고유한 Request ID를 부여하여 요청 흐름을 추적할 수 있도록 합니다.

---

## 7. 캐싱 전략 (Caching Strategy)
- **적용 기준**: 읽기 빈도가 높고 변경 빈도가 낮은 데이터에 우선 적용합니다 (예: 설정값, 코드 테이블, 자주 조회되는 목록).
- **캐시 무효화**: 데이터 변경 시 관련 캐시를 즉시 무효화하는 전략을 함께 정의합니다. TTL(Time To Live) 기반을 기본으로 하되, 중요 데이터는 이벤트 기반 무효화를 병행합니다.
- **캐시 레이어**: 인메모리 캐시(로컬)와 분산 캐시(Redis 등)의 적용 기준을 구분합니다. 단일 인스턴스 환경이면 인메모리로 시작하고, 다중 인스턴스 확장 시 분산 캐시로 전환합니다.

## 8. 역할별 특별 지침

### BE-Plan (설계자) 특별 지침
- **인프라 결정**: 프로젝트 착수 전 PRD를 철저히 분석하여 베이스 인프라(DB, 서버 런타임 플랫폼 등)를 명확히 정의하고, `architecture.md` 문서로 구조화해야 합니다.
- **API 설계**: API 명세서 설계 시 RESTful 원칙을 철저히 준수하고, 요청/응답 스키마(Data Type, 필수 여부 등)를 빠짐없이 정의합니다.
- 시스템 아키텍처 다이어그램 설계 시 데이터 흐름의 병목 예상 지점 및 시스템 컴포넌트를 명확히 식별하여 문서에 명시합니다.
- **산출물 필수 포함 항목**: BE-Plan 단계의 산출물에는 아래 항목을 반드시 포함합니다.
    - 시스템 아키텍처 다이어그램 (컴포넌트 간 관계 및 데이터 흐름)
    - API 명세서 (엔드포인트, 요청/응답 스키마, 인증 방식, 에러 코드)
    - 환경별 설정 및 인프라 구성 기준
    - 비기능 요구사항 정의 (성능 목표, 보안 요건, 가용성 기준)
- **타 역할 핸드오프(Handoff) 체크리스트**:
    - **to DB-Plan**: 데이터 구조 설계를 위한 논리적 모델링 초안, 엔티티 간 관계 요구사항, 캐싱 전략.
    - **to FE-Plan**: 프론트엔드 연동을 위한 확정된 API 명세서, 인증 메커니즘 가이드, 웹소켓 등 통신 스펙 명세.
    - **to BE-Act**: 완벽한 아키텍처 문서, 핵심 비즈니스 로직 플로우, 구현에 필요한 인터페이스 스펙.

### BE-Review (검수자) 특별 지침
- API 명세나 아키텍처 문서에서 인증/인가, 보안 등의 누락 사항이 없는지 예리하게 검토합니다.
- N+1 쿼리 발생 가능성이나 비효율적인 동기 처리 구간을 식별하되, 문서를 직접 수정하지 않고 피드백만 남깁니다.
- **검수 중점 사항 (Review Checklist)**:
    - [ ] 작성된 문서는 백엔드 작업 폴더(`docs/04. be/`, `backend/`) 밖의 리소스(타 파트 문서)를 직접 침범/수정하지 않았는가? (도메인 권한 엄수)
    - [ ] 컨트롤러(입력 검증) - 서비스(비즈니스 명세) - 레포지토리(DB명세)의 계층형 아키텍처가 논리적으로 잘 분리되어 있는가?
    - [ ] 에러 코드 명세 및 Global Exception Handler 전략 등 예외/실패 상황(Edge Case)에 대한 처리가 정의되어 있는가?
    - [ ] 인증/인가 처리가 미들웨어/인터셉터에 분리되어 있으며, 환경변수 및 Secret 관리 원칙(4절)을 준수하고 있는가?

### BE-Act (실행자) 특별 지침
- TDD(Red-Green-Refactor) 원칙에 입각하여 핵심 비즈니스 로직(Service Layer)부터 구현 및 테스트합니다.
- 예외 처리는 개별 try-catch를 남발하지 않고, 글로벌 예외 처리기(Global Exception Handler)를 활용해 구현합니다.
- **검수 요청 전 자체 체크리스트 (Done Criteria)**:
    - [ ] 빌드 에러/경고가 없으며, 정적 타입 검증 및 린터(Linter) 규칙을 통과하는가?
    - [ ] Service Layer는 타 계층(Controller 유입물 등)에 강결합되지 않고, 단위 테스트가 가능하도록 의존성 주입이 되어 있는가?
    - [ ] 데이터베이스 비밀번호, API Key 등의 민감한 환경변수가 코드에 하드코딩되지 않았는가?
    - [ ] 핵심 Service Layer 테스트 커버리지가 80% 이상 달성되었는가? (3절 TDD 기준)
