# 기획 파트 스탠다드 및 가이드라인 (PO)

이 문서는 서비스 기획(PO-Plan, PO-Review, PO-Act) 시 일관성과 완성도를 높이기 위한 가이드라인입니다.
아래 섹션 1~5는 공통 원칙이며, 섹션 6은 각 역할별 세부 지침과 템플릿을 다룹니다.

---

## 0. AI 협업 및 프로젝트 특화 원칙 (Core Workflow)

실무 프로젝트 경험을 바탕으로, AI 파트너와 협업 시 아래 원칙을 최우선으로 적용합니다.

- **도메인 권한 엄수 (Cross-Domain Read-Only)**: 기획 에이전트(`po-plan`, `po-rv`, `po-act`)는 기획 전용 작업 폴더(`docs/01. po/`) 및 스탠다드 로컬 파일(`.agents/standards/PO_GUIDE.md`) 내에서만 쓰기/수정 권한을 가집니다. 기술(FE/BE) 문서나 코드, 디자인 문서를 수정해야 할 경우, 절대 직접 덮어쓰지 않고 `docs/01. po/` 하위에 수정 제안서 마크다운(.md) 파일(예: `docs/01. po/fe_modification_request.md`)을 작성한 뒤 유저에게 해당 에이전트를 호출하도록 가이드합니다.
- **역할 간 경계 준수**: PO는 'What(무엇을)'과 'Why(왜)'에 집중합니다. 'How(어떻게)'는 UI/BE/FE 설계 단계에서 구체화되도록 열어두되, 서비스의 핵심 비즈니스 정책(예: 정산 공식, 데이터 보존 주기 등)은 명확히 정의합니다.
- **경험 중심 기획 (Experience-First)**: 단순 기능 나열이 아닌, 전체적인 '코어 경험 테마'(예: 감성 키워드, 핵심 인터랙션 원칙, 브랜딩 방향성)를 PRD 초기에 정의하여 이후 디자인/개발 단계의 정체성을 명확하게 가이드합니다.
- **환경 및 제약 조건 파악**: 프로젝트의 타겟 환경(운영체제, 인프라 제약, 브라우저 환경 등)에 따른 제약을 기획 단계에서 선제적으로 인지하고 현실에 맞는 개발 범위를 설정합니다.

---

## 1. 요구사항 명세서 (PRD) 핵심 원칙

- **문제 정의 명확화**: 사용자가 겪는 문제(Pain Point)와 해결하고자 하는 목표를 명쾌하게 정의합니다.
- **사용자 스토리 (User Story)**: 아래 표준 형식을 따릅니다.
  - 형식: `As a [역할], I want [기능], So that [비즈니스 가치]`
  - 예시: "As a 로그인한 유저, I want 상품을 장바구니에 추가할 수 있기를, So that 관심 상품을 모아두고 한번에 구매할 수 있다."
  - 핵심: "So that" 부분에 반드시 **사용자/비즈니스 관점의 가치**를 명시합니다. 단순 기능 설명이 아닌, 왜 이 기능이 필요한지를 담아야 합니다.
- **유스케이스 & 시나리오**: 긍정적 시나리오(Happy Path)뿐만 아니라, 예외 상황(Edge Case)에 대한 동작 정책도 반드시 명시합니다.

## 2. 문서화 구조 표준

기획 문서는 다음의 구조를 기본으로 세팅합니다.

1. **Overview**: 목적, 문제 정의 및 **경험 컨셉(Theme)**
2. **Success Metrics (KPI)**: 성공을 판단할 데이터 지표
3. **Features & Requirements**: 상세 기능 요구사항 (User Story) 및 **핵심 비즈니스 로직(공식)**
4. **비기능 요구사항 (NFR)**: 성능(응답속도), 보안, **접근성(a11y)**, 확장성
5. **UI/UX 상태 정책**: **Empty State**, **Loading State**, **Error State**에 대한 기본 정의
6. **제약 조건 & 리스크**: 기술적/환경적 제약(Local-First 등)
7. **Out of Scope**: 이번 페이즈 제외 항목

### Success Metrics 작성 가이드

지표는 **측정 가능한 수치**로 정의하며, 아래 유형을 참고하여 최소 2개 이상 설정합니다.

| 지표 유형            | 예시                                     |
| -------------------- | ---------------------------------------- |
| 전환(Conversion)     | 회원가입 전환율 30% 이상 달성            |
| 활성(Engagement)     | 일평균 세션 시간 5분 이상                |
| 리텐션(Retention)    | 7일 재방문율 40% 이상                    |
| 만족도(Satisfaction) | NPS 50점 이상                            |
| 효율(Efficiency)     | 특정 태스크 완료 시간 기존 대비 20% 단축 |

## 3. 검토 및 커뮤니케이션 (Review & Act)

- **우선순위 부여**: 모든 기능(Task)에는 MoSCoW 방법론을 적용해 우선순위를 매깁니다.
  - **Must**: 없으면 출시 불가 / **Should**: 중요하지만 대안 가능 / **Could**: 있으면 좋은 수준 / **Won't**: 이번 스코프 제외
- **디자인/개발 피드백 수용**: 기술적 구현 제약이나 UX상 모순이 있는 부분은 해당 파트의 피드백을 수용합니다. 단, 기획 변경 시에는 변경 사유와 영향 범위를 문서에 기록합니다.
- **작업 지시 가이드**: 개발팀에 티켓을 넘길 때(PO-Act), As-Is와 To-Be를 명백하게 구분해 전달합니다.

---

## 4. 기획 확정/승인 프로세스

기획 문서는 아래 절차를 거쳐 확정됩니다.

1. **PO-Plan**: 기획 초안 작성 및 제출
2. **PO-Review**: 검수 체크리스트 기반 리뷰 수행, 피드백 문서 작성
3. **PO-Plan**: 피드백 반영 후 수정본 제출 (필요 시 2~3 반복)
4. **승인 조건**: 아래 항목을 모두 충족하면 확정
   - PO-Review 체크리스트 전 항목 통과
   - Must 우선순위 기능의 User Story 및 Edge Case 완비
   - Success Metrics 최소 2개 이상 정의
5. **PO-Act**: 확정된 기획을 기반으로 개발 티켓 작성 및 전달

## 5. 문서 관리

### 버전 관리

- 기획 문서 상단에 아래 형식의 변경 이력을 유지합니다.

| 버전 | 날짜       | 작성자 | 변경 내용             |
| ---- | ---------- | ------ | --------------------- |
| v1.0 | YYYY-MM-DD | OOO    | 초안 작성             |
| v1.1 | YYYY-MM-DD | OOO    | PO-Review 피드백 반영 |

### 용어 정의 (Glossary)

- 도메인 고유 용어나 프로젝트 내에서 혼동될 수 있는 용어는 기획 문서 말미 또는 별도 파일에 정리합니다.
- 형식: `용어 | 정의 | 비고` (표 형태)
- 새로운 용어가 등장할 때마다 갱신하며, 팀 내 용어 통일의 기준으로 삼습니다.

## 6. 역할별 특별 지침

### PO-Plan (설계자) 특별 지침

- PRD 작성 시 기술적 구현 방법을 직접 고민하지 말고, 철저히 '비즈니스 목적'과 '사용자 가치'에 기반하여 명세합니다. 단, 비즈니스 로직이 데이터 구조나 API 설계에 직접적 영향을 주는 경우에는 기술팀과 사전 협의합니다.
- 예외 상황(Edge Case) 설계 시, 누락된 정책 시나리오가 없는지 꼼꼼히 체크합니다.
- **타 역할 핸드오프(Handoff) 체크리스트**:
  - **to UI-Plan**: 화면 목록, 각 화면의 핵심 목적, 인터랙션 중요도(애니메이션 등).
  - **to BE-Plan**: 데이터 엔티티 관련 핵심 정책(예: Soft Delete 및 보존 정책 등), 수식 및 비즈니스 계산 공식.
  - **to FE-Plan**: 성능 목표 수치, 웹 접근성(a11y) 기준, 상태별(Empty/Error/Loading) 동작 UI 가이드 스펙.

### PO-Review (검수자) 특별 지침

- 기획 내용을 절대로 직접 수정하지 말고, 구조화된 리뷰 피드백만 남깁니다.
- 아래 체크리스트를 기준으로 검토하며, 검수 결과는 템플릿에 맞춰 작성합니다.

#### 검수 체크리스트

| #  | 검토 항목       | 확인 내용                                                                     |
| -- | --------------- | ----------------------------------------------------------------------------- |
| 1  | 문제 정의       | Pain Point와 목표가 명확히 서술되어 있는가                                    |
| 2  | User Story      | 표준 형식(As a/I want/So that)을 따르며, 비즈니스 가치가 명시되어 있는가      |
| 3  | Success Metrics | 측정 가능한 KPI가 2개 이상 정의되어 있는가                                    |
| 4  | 기능 요구사항   | 각 기능의 입력/출력/동작이 구체적으로 기술되어 있는가                         |
| 5  | 비기능 요구사항 | 성능, 보안 등 품질 속성이 고려되어 있는가                                     |
| 6  | Edge Case       | 예외 상황에 대한 동작 정책이 누락 없이 정의되어 있는가                        |
| 7  | 우선순위        | 모든 기능에 MoSCoW 우선순위가 부여되어 있는가                                 |
| 8  | Out of Scope    | 제외 항목이 명시되어 범위 혼동의 여지가 없는가                                |
| 9  | 논리적 일관성   | 기능 간 모순이나 정책 충돌이 없는가                                           |
| 10 | 용어 통일       | 도메인 용어가 문서 전체에서 일관되게 사용되고 있는가                          |
| 11 | 도메인 권한     | 타 파트 문서(FE/BE/UI) 직접 수정 없이, 제안서(.md) 형태로 요청이 이루어졌는가 |

#### 검수 결과 템플릿

```markdown
# 기획 검수 결과

## 검수 대상
- 문서: [파일명 또는 기획 제목]
- 버전: [v1.0]
- 검수자 : 
- 검수일시 : | [날짜] [시간]|

## 종합 판정
- [ ] 승인 (수정 없이 진행 가능)
- [ ] 조건부 승인 (경미한 수정 후 진행)
- [ ] 반려 (주요 항목 수정 후 재검수 필요)

## 체크리스트 결과
| # | 항목 | Pass/Fail | 비고 |
|---|------|-----------|------|
| 1 | 문제 정의 | | |
| 2 | User Story | | |
| ... | ... | | |

## 상세 피드백
### 승인 항목
- [잘 작성된 부분에 대한 코멘트]

### 수정 필요 항목
- [항목]: [구체적 수정 방향]

### 보완 필요 항목
- [항목]: [추가로 필요한 내용]
```

### PO-Act (실행자) 특별 지침

- 확정된 기획만을 대상으로 티켓을 작성합니다 (미승인 기획은 티켓화하지 않습니다).
- 개발 우선순위(MoSCoW)가 명확하게 부여되었는지 확인하고 작업을 확정합니다.
- 아래 템플릿을 기준으로 티켓을 작성합니다.

#### 개발 티켓 템플릿

```markdown
# [티켓 제목]

## 우선순위
- MoSCoW: [Must / Should / Could / Won't]

## 관련 기획
- 기획 문서: [파일명 또는 링크]
- User Story: As a [역할], I want [기능], So that [가치]

## As-Is (현재 상태)
- [현재 동작 또는 현재 상태 설명]

## To-Be (목표 상태)
- [구현 후 기대되는 동작 또는 상태 설명]

## 상세 요구사항
- [ ] [구체적 구현 항목 1]
- [ ] [구체적 구현 항목 2]

## Edge Case / 예외 처리
- [예외 상황]: [처리 정책]

## 완료 조건 (Done Criteria)
- [ ] [검증 가능한 완료 기준]
```
