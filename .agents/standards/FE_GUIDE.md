# 프론트엔드 스탠다드 및 가이드라인 (FE)

이 문서는 프론트엔드 설계, 구현, 리뷰, 핸드오프 전 과정에서 공통으로 따르는 단일 원본입니다.
`fe-plan`, `fe-rv`, `fe-act`는 모두 이 문서를 기준으로 판단하며, 스킬 문서는 이 기준을 리뷰나 반복 작업에 적용하는 보조 수단으로만 사용합니다.

---

## 0. 문서 목적과 적용 범위

- 적용 대상: `docs/06. fe/`, `frontend/`, 프론트엔드 라우팅/상태/스타일/테스트 코드
- 적용 단계: 설계(`fe-plan`), 리뷰(`fe-rv`), 구현(`fe-act`)
- 우선순위: 본 문서 > 스킬 문서 > 임시 작업 메모
- 목표: 화면 구조, 구현 기본값, 리뷰 기준, 완료 조건을 한 문서에서 제공

---

## 1. AI 협업 및 프론트엔드 특화 원칙

- **도메인 권한 엄수**: 프론트엔드 에이전트는 `docs/06. fe/`, `frontend/`, `.agents/standards/FE_GUIDE.md` 범위에서만 직접 수정합니다.
- **크로스 도메인 읽기 전용**: UI, BE, DB, PO 문서와 코드는 읽기만 가능하며, 수정이 필요하면 제안서를 남깁니다.
- **Experience-First**: PO와 UI가 정한 사용자 경험을 정확하게 구현하는 것을 우선합니다.
- **State Completeness**: 로딩, 에러, 빈 화면, 권한 없음, 재시도 상태를 빠뜨리지 않습니다.
- **4-Phase Strategy**: 기반 환경 -> Presentational UI -> 데이터/상태 연동 -> 접근성/애니메이션 폴리싱 순으로 작업합니다.
- **안전한 핸드오프**: 구현 완료 후 다음 담당자가 바로 이어받을 수 있도록 완료 범위, 미완 항목, 리스크를 남깁니다.

---

## 2. 설계 원칙

### 2.1 화면/상태/데이터 흐름 분리

- 화면 구조, 사용자 상호작용, 서버 연동, 상태 저장 위치를 설계 단계에서 분리해 정의합니다.
- 서버 상태와 UI 상태를 같은 저장소에 섞지 않습니다.
- 컴포넌트 트리와 상태 위치는 문서에서 먼저 고정합니다.

### 2.2 컴포넌트 경계와 책임

- Presentational 컴포넌트와 데이터/상태를 다루는 Container 또는 Hook을 분리합니다.
- 한 컴포넌트가 API 호출, 비즈니스 규칙, 복잡한 레이아웃까지 모두 담당하지 않게 합니다.
- 재사용 목적이 없는 로컬 로직은 무리해서 공용 추상화하지 않습니다.

### 2.3 반응형 및 접근성

- 모바일 우선을 기본으로 합니다.
- 시맨틱 HTML을 우선 사용하고, 비시맨틱 상호작용 요소는 예외적으로만 허용합니다.
- 키보드 탐색, 포커스 흐름, aria-label/alt를 초기 설계에서 고려합니다.

---

## 3. 구현 컨벤션

### 3.1 파일/폴더 배치 규칙

- 페이지, 기능, 공통 컴포넌트, 훅, 스토어, API 클라이언트를 역할별로 분리합니다.
- 한 파일에 UI, 네트워크 호출, 상태 머신, 데이터 변환을 과도하게 몰아넣지 않습니다.
- 기능 단위 폴더를 우선하되, 전역 공용 컴포넌트는 명확한 공통성이 있을 때만 분리합니다.

### 3.2 네이밍 규칙

- 컴포넌트는 `PascalCase`, 훅은 `use*`, 유틸과 함수는 `camelCase`를 사용합니다.
- boolean 값은 `is`, `has`, `should`, `can` 접두어를 사용합니다.
- 임시 이름(`data`, `item`, `temp`) 대신 도메인 의미를 드러냅니다.

### 3.3 컴포넌트 작성 규칙

- JSX는 가능한 한 선언적으로 유지하고 조건 분기는 상단 변수 또는 보조 함수로 분리합니다.
- 리스트 렌더링에서 index를 기본 key로 사용하지 않습니다.
- 비즈니스 로직이 많은 경우 컴포넌트 밖 훅이나 서비스 함수로 분리합니다.
- 로딩, 에러, 빈 화면을 기본적으로 포함합니다.

### 3.4 훅과 상태 관리 규칙

- 훅 규칙을 위반하지 않습니다.
- 로컬 상태로 충분한 값은 전역 스토어에 올리지 않습니다.
- 전역 상태는 아래 경우에만 허용합니다.
  - 인증/세션
  - 테마/로케일
  - 다수 페이지 공유 상태
  - props drilling 3단계 초과
- 파생 가능한 값을 별도 state로 중복 저장하지 않습니다.

### 3.5 서버 상태 및 API 연동 규칙

- 서버 상태는 별도 캐싱 계층 또는 명확한 API 클라이언트 계층을 통해 다룹니다.
- API 호출 코드는 컴포넌트 본문에 직접 흩뿌리지 않습니다.
- mutation은 낙관적 업데이트보다 안전한 캐시 무효화 또는 재조회 전략을 기본값으로 둡니다.
- 중복 제출 방지를 위해 pending 상태 제어를 포함합니다.

### 3.6 스타일링 규칙

- 프로젝트에서 채택한 스타일링 방식만 사용합니다.
- 인라인 스타일과 임의의 스타일 혼용을 기본값으로 두지 않습니다.
- 디자인 토큰, spacing, typography, color 사용을 일관되게 유지합니다.

### 3.7 접근성 규칙

- 아이콘 버튼, 이미지, 상태 전달 UI에는 적절한 접근성 속성을 제공합니다.
- `<button>`, `<a>`, `<label>` 같은 시맨틱 요소를 우선 사용합니다.
- `div`나 `span`으로 상호작용 요소를 만들었다면 role, tabIndex, Enter/Space 대응, 포커스 표시를 함께 제공합니다.
- 모달, 드롭다운, 토스트 등은 포커스 이동과 닫힘 동작을 설계합니다.

### 3.8 성능 규칙

- `useMemo`, `useCallback`, `React.memo`는 측정된 병목이 있을 때만 적용합니다.
- 참조 churn이나 불필요한 전역 구독을 줄이는 쪽을 먼저 봅니다.
- `useSyncExternalStore` 사용 시 snapshot 함수가 불필요하게 새 객체를 만들지 않게 합니다.
- 페이지 단위 code splitting과 lazy loading을 기본으로 고려합니다.

---

## 4. 테스트 최소 기준

- 핵심 화면은 로딩, 성공, 실패, 빈 화면 상태를 검증합니다.
- 복잡한 훅과 스토어는 상태 전이와 에러 경로를 검증합니다.
- 핵심 사용자 흐름은 페이지 또는 기능 단위 smoke 테스트를 갖습니다.
- 약한 assertion이나 DOM 존재 여부만 확인하는 테스트에 머무르지 않습니다.

---

## 5. 리뷰 체크포인트

### 5.1 정확성

- 훅 규칙, 상태 전이, 중복 요청 방지, 에러 복구가 올바른가

### 5.2 렌더 성능

- 참조 churn, 과도한 구독, 불필요한 재계산이 있는가

### 5.3 상태 관리

- 로컬/전역/서버 상태의 위치가 타당한가
- 파생 상태를 중복 저장하지 않는가

### 5.4 타입 안전성

- `any`, 무분별한 type assertion, nullable 값 미처리가 없는가

### 5.5 보안

- XSS 가능 경로, 위험한 URL 주입, 민감 정보 노출이 없는가

### 5.6 접근성

- 시맨틱 마크업, 키보드 탐색, 포커스 흐름, aria 속성이 충분한가

### 5.7 프로젝트 관례 준수

- 폴더 구조, 스타일링 방식, API 연동 위치, 네이밍 규칙이 일관적인가

---

## 6. Done Criteria

- 빌드와 린트를 통과한다.
- 로딩/에러/빈 화면 상태가 구현되어 있다.
- 중복 요청 방지와 기본 접근성이 반영되어 있다.
- API 연동과 상태 관리 위치가 문서와 일치한다.
- 필요한 테스트가 추가 또는 갱신되었다.

---

## 7. Handoff 기준

### 7.1 to FE-Review

- 변경 범위 요약
- 남은 UI/상태 리스크
- 테스트 실행 결과
- 접근성 또는 반응형 확인 범위

### 7.2 to BE

- 필요한 API 계약 변경
- 에러 응답 처리 요구사항
- 서버 상태 갱신 조건

### 7.3 to UI

- 실제 구현에서 드러난 화면 제약
- 상호작용과 접근성 관련 피드백

---

## 8. 역할별 특별 지침

### FE-Plan

- 컴포넌트 트리, 상태 위치, 데이터 의존성을 문서화합니다.
- Props와 화면 상태를 명시해 구현 시 추측이 없도록 합니다.

### FE-Review

- 설계와 코드의 정합성, 접근성, 상태 분리, mutation 처리 품질을 중심으로 리뷰합니다.
- 구조적 문제는 직접 수정 대신 findings로 남기고 필요한 경우 설계 단계로 되돌립니다.

### FE-Act

- 기존 디자인 시스템과 컨벤션을 우선 따릅니다.
- 새 정책을 만들기보다 확정된 규칙 안에서 구현을 마무리합니다.
