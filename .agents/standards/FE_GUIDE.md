# 프론트엔드/디자인 스탠다드 및 가이드라인 (FE)

이 문서는 프론트엔드 개발 및 디자인(FE-Plan, FE-Review, FE-Act) 시 AI 에이전트 간의 일관성과 협업 효율성을 높이기 위한 가이드라인입니다.

---

## 0. AI 협업 및 프론트엔드 특화 원칙 (Core Workflow)

실무 프로젝트 경험을 바탕으로, AI 파트너와 협업 시 아래 원칙을 최우선으로 적용합니다.

- **도메인 권한 엄수 (Cross-Domain Read-Only)**: 프론트엔드 에이전트(`fe-plan`, `fe-rv`, `fe-act`)는 프론트엔드 전용 작업 폴더(`docs/06. fe/`, `frontend/` 등) 및 스탠다드 로컬 파일(`.agents/standards/FE_GUIDE.md`) 내에서만 쓰기/수정 권한을 가집니다. 타 도메인 에이전트가 관리하는 파일(`PRD.md`, `UI_GUIDE.md`, 백엔드 코드 등)은 절대 직접 덮어쓰거나 편집하지 않습니다. 만약 **타 파트 문서에 대한 수정이나 제안이 필요할 경우, 직접 수정하는 대신 해당 의견을 `docs/` 하위 디렉터리에 별도의 마크다운(.md) 파일(예: `docs/06. fe/ui_modification_request.md`)로 작성**한 뒤 유저에게 해당 에이전트 호출을 가이드합니다.
- **컨텍스트 최적화 (Targeted Context)**: 프론트엔드 설계/구현 시 전체 코드를 모두 주입하지 않고, 관련된 기획(`PRD.md`), UI 디자인 시스템(`design_system.md`), 그리고 현재 작업 중인 특정 컴포넌트 파일만 타겟팅(`@` 멘션)하여 토큰을 절약합니다.
- **경험 중심 구현 (Experience-First)**: PO가 정의한 '경험 테마(Theme)'를 시각적·상호작용적 요소(Tailwind, Framer Motion 등)로 충실하게 번역하는 것을 목표로 합니다.
- **상태의 명시적 정의 (State Completeness)**: `Loading`, `Error`, `Empty` 상태 처리를 기획 문서에서 인계받아, 컴포넌트 설계 단계부터 누락 없이 명세합니다.
- **표준화된 개발 4단계 (4-Phase Strategy)**: 기반 환경 구성(Theme) → Dumb (Presentational) UI 컴포넌트 구현 → 비즈니스 로직(API, Container) 연동 → 마이크로 애니메이션 및 접근성 폴리싱(Polish) 순서로 작업을 청크(Chunk) 분할하여 진행합니다.
- **핸드오프 (Handoff) 패턴 활용**: 설계 완료 후 구현으로, 구현 완료 후 검수로 넘어갈 때 작업의 맥락이 끊기지 않도록 `docs/06. fe/HANDOFF.md` 경로에 인수인계 문서(최소 포함 항목: 완료 작업 요약, 미완 작업, 다음 에이전트를 위한 컨텍스트 및 주의사항)를 작성하여 전달합니다.

## 1. UI 프레임워크 및 디자인 시스템

프로젝트 시작 시 기획 문서(`PRD.md`)나 설계 문서(`fe_development_plan.md`)에 확정된 기술 스택을 명시해야 하며, 별도 정의가 없다면 아래의 **기본 권장 스택**을 따릅니다.

| 분류 | 기본 권장 스택 | 참고 사항 (대체 가능 스택) |
| --- | --- | --- |
| 프레임워크 | Next.js App Router | Vite + React (SPA) 등 |
| 스타일링 | Tailwind CSS | Vanilla CSS, UI 프레임워크에 따른 커스텀 |
| UI 컴포넌트 | Shadcn UI | Radix UI, 접근성 속성(a11y) 내장 라이브러리 |
| 폼 관리 | React Hook Form + Zod | 성능 이점이 큰 비제어 컴포넌트 기반 라이브러리 |

- **스타일링 원칙**: 프로젝트에 채택된 스타일링 방식(예: Tailwind CSS)을 최우선으로 사용하며 임의의 인라인 스타일은 금지합니다.
- **컴포넌트 라이브러리**: 채택된 핵심 라이브러리의 컴포넌트 철학을 따르며, 일관성 있는 디자인 토큰(Color, Typography 등)을 전역으로 관리합니다.
- **접근성(a11y)**: 시맨틱 태그 및 WAI-ARIA 속성을 사용하여 스크린 리더 등 보조 기기에 기본적으로 완전히 대응해야 합니다.
- **반응형 레이아웃 전략 (Responsive Design)**:
  - 특별한 예외가 없는 한 **모바일 우선(Mobile-First)** 접근 방식을 기본으로 채택합니다.
  - 컨테이너 너비 기반의 유연한 조정을 위해 `@container` 쿼리 사용을 권장하며, 미디어 쿼리는 일관된 브레이크포인트 단위로 관리합니다.

## 2. 컴포넌트 및 상태 관리 구조
- **단일 책임 원칙 (SRP)**: UI 렌더링을 담당하는 Presentational 컴포넌트와, 비즈니스 로직(API 호출, 상태 조작 등)을 담당하는 Container 컴포넌트를 명확히 분리합니다.
- **Custom Hook 추출**: 컴포넌트 내에 복잡한 로직이 집중되지 않도록, 관련된 상태와 로직은 Custom Hook으로 분리합니다.
- **전역 상태 최소화**: `Context API`나 전역 상태 라이브러리(Zustand 등)의 사용은 최소화합니다. 서버 상태는 별도의 캐싱 계층(SWR, React Query 등)에 위임합니다.
  - **전역 상태 허용 기준** (아래 경우에만 전역 상태 사용을 허용):
    - 인증/세션 정보: 로그인 사용자 정보, 토큰 등 앱 전반에서 참조하는 데이터
    - 테마/로케일 설정: 다크모드 토글, 언어 설정 등 UI 전역 설정
    - Props Drilling 3단계 초과: 3단계 이상 깊이로 Props를 전달해야 하는 경우
    - 복수 페이지 간 공유 상태: 장바구니, 알림 배지 카운트 등 여러 라우트에서 동시에 읽고 쓰는 데이터
  - 위 기준에 해당하지 않는 데이터는 컴포넌트 로컬 상태(`useState`)로 관리합니다.
- **API 도메인 연동 및 뮤테이션 (Mutation) 원칙**:
  - `POST`, `PUT`, `DELETE` 요청 시, 빠른 UX가 극도로 중요한 경우가 아니라면 **낙관적 업데이트(Optimistic UI)는 지양**하고 비즈니스 로직의 안전성을 위해 **캐시 무효화(Cache Invalidation)** 후 재조회하는 방식을 기본 채택합니다.
  - 연동 중 중복 요청을 방지하기 위해 버튼 비활성화(`isPending`, `isCompleting`) 처리를 강제합니다.

## 3. 클린 코드 및 클린 아키텍처
- **명칭(Naming)**: boolean 변수명은 `is`, `has`, `should` 등의 접두어를 붙여 명확하게 짓습니다. (예: `isOpen`, `hasError`)
- **매직 스트링/넘버**: 로직 내에서 직접적인 숫자나 문자열 사용을 지양하고, 상수로 분리하여 의미를 부여합니다.
- **엣지 케이스 처리**: 로딩(`Loading`), 에러(`Error`), 빈 화면(`Empty`)의 3가지 상태에 대한 UI 대응을 모든 리스트 및 데이터 Fetching 영역에 필수로 구현합니다.
- **에러 바운더리(Error Boundary) 전략**:
  - 앱 최상위에 글로벌 Error Boundary를 배치하여 예기치 못한 런타임 오류 시 Fallback UI(재시도 버튼 포함)를 표시합니다.
  - 주요 기능 단위(페이지, 독립 위젯 등)별로 지역 Error Boundary를 추가하여, 특정 영역의 오류가 전체 앱을 중단시키지 않도록 격리합니다.
  - Error Boundary에서 포착한 오류는 로깅 서비스(Sentry 등)로 전송하여 모니터링합니다.
  - API 호출 에러는 Error Boundary가 아닌 React Query/SWR의 `onError` 핸들러 또는 try-catch에서 처리합니다.

## 4. 라우팅 전략
- **파일 기반 라우팅 (Next.js 권장)**: 파일 기반 라우터를 사용하는 경우, 라우트 그룹 기능을 활용하여 URL에 영향을 주지 않고 관련 페이지/컴포넌트를 논리적으로 묶어 결합도를 낮춥니다.
- **레이아웃 분리**: 공통 레이아웃 파일과 각 페이지/위젯별 로딩, 에러 UI(`loading.tsx`, `error.tsx` 등)를 스택 규칙에 맞춰 명확히 정의합니다.
- **SPA (React Router 등)**: 라우트 선언을 한 곳으로 집중시키고, 인증 보호 라우트(`ProtectedRoute`) 로직을 별도 컴포넌트로 분리합니다.
- 프레임워크와 상관없이 URL 설계(경로 명명 구조, 쿼리 파라미터 규칙)는 기획/설계 단계에서 우선 확정해야 합니다.

## 5. 폼 관리 전략
- **구조 최적화**: 복잡하고 타이핑에 따른 과도한 리렌더가 발생하는 폼을 막기 위해 비제어 컴포넌트 패턴 라이브러리(예: `React Hook Form`) 사용을 우선적으로 고려합니다.
- **선언적 유효성 검증**: 스키마 기반 검증 라이브러리(예: `Zod`)와 연동하여 폼 로직과 유효성 검사 규칙을 도메인 레벨로 분리하고 정리합니다.
- **에러 표시**: 필드별 인라인 에러 메시지를 즉시 표시하며, 서버 측 검증 에러도 해당 필드에 매핑하여 보여줍니다.
- **복잡한 폼**: 다단계(Wizard) 폼은 단계별로 컴포넌트를 분리하고, 폼 전체 파이프라인 상태는 최상위 폼 레이아웃에서 관리합니다.

## 6. 성능 최적화 기준
- **Code Splitting / Lazy Loading**: 페이지 단위로 `React.lazy` 또는 프레임워크의 동적 import를 적용하여 초기 번들 크기를 최소화합니다.
- **Web Vitals 목표치**:
  - LCP(Largest Contentful Paint): 2.5초 이내
  - FID(First Input Delay) / INP(Interaction to Next Paint): 200ms 이내
  - CLS(Cumulative Layout Shift): 0.1 이하
- **메모이제이션**: `React.memo`, `useMemo`, `useCallback`은 측정된 성능 병목에 대해서만 적용하며, 무분별한 사전 최적화는 지양합니다.
- **이미지/에셋 관리**:
  - 이미지는 `next/image` 또는 동등한 최적화 컴포넌트를 통해 자동 리사이징, WebP 변환, lazy loading을 적용합니다.
  - 아이콘은 SVG 인라인 또는 아이콘 라이브러리(`lucide-react` 등)로 통일하며, PNG/JPG 아이콘 사용을 지양합니다.
  - 정적 에셋은 `public/` 디렉터리에 일관된 폴더 구조(`images/`, `fonts/` 등)로 관리합니다.

## 7. 역할별 특별 지침

### FE-Plan (설계자) 특별 지침
- 컴포넌트 명세 작성 시 반드시 Prop의 타입과 필수 여부를 명시합니다.
- 상태(State)가 어느 계층(전역/로컬/서버 캐시)에 위치해야 하는지 명확히 설계하여 문서화합니다.
- **타 역할 핸드오프(Handoff) 수신/발신 체크리스트**:
  - **from PO/UI-Plan**: 기획 요구사항(PRD)과 테마, 디자인 시스템, 접근성(a11y) 기준 수령.
  - **to FE-Act**: 명확한 컴포넌트 트리, 폴더 구조, Props 인터페이스, 뷰 렌더링 명세 전달.
- **산출물 형식**: 설계 결과는 아래 항목을 포함하는 마크다운 문서로 작성합니다.
  - 컴포넌트 트리 구조도 (텍스트 또는 다이어그램)
  - 컴포넌트별 Props 인터페이스 (타입, 필수 여부, 기본값)
  - 상태 관리 맵 (상태명, 위치, 갱신 트리거)
  - 페이지별 라우트 경로 및 데이터 의존성 목록

### FE-Review (검수자) 특별 지침
- **필수 검수 체크리스트 (Review Criteria)**:
  - [ ] Mobile-First 및 반응형 레이아웃 분기점 준수 여부
  - [ ] 시맨틱 마크업, `aria-label`, 키보드 내비게이션 등 웹 접근성(a11y) 위반 요소 유무
  - [ ] 컴포넌트가 단일 책임 원칙(SRP)에 따라 시각적 요소(View)와 비즈니스 로직으로 적절히 분리되었는가
  - [ ] Mutation 처리 시 중복 요청 방지(`isPending`, `isCompleting`) 및 적절한 캐시 무효화 정책이 반영되었는가
  - [ ] 로딩(Loading), 에러(Error), 빈 화면(Empty State)에 대한 엣지 케이스 UI 대응 여부
- 철저하게 설계 문서 및 소스 코드의 **읽기 권한만 행사**하며 절대 직접 문서를 편집하거나 코드를 시도/수정하지 않습니다. (단, 에러나 오타의 단순 지적을 넘어선 구조적 아키텍처 변경 건이면, 직접 코드를 고치는 대신 `fe-plan`을 호출하여 설계를 먼저 수정하게끔 유도합니다.)
- 검수 후 도출된 엣지 케이스 및 개선 요구 사항은 다음 단계인 `FE-Act`가 즉시 작업할 수 있도록 리포트 형태로 정리하여 출력 또는 문서화합니다.

### FE-Act (실행자) 특별 지침
- 코드를 구현할 때 프로젝트 환경에 명시된 UI 기반 철학과 디자인 시스템 지침 규칙을 엄격하게 지켜서 뷰(View)를 완성합니다.
- 컴포넌트 파일 작성 시 데이터 Fetching 로직(Custom Hook 등)과 화면 렌더링 영역(UI)을 명확하게 분리하여 작성(단일 책임 원칙)합니다.
- **검수 요청 전 자체 체크리스트 (Done Criteria)**:
  - [ ] 코드 Lint 에러 및 빌드 경고가 없는 상태인가?
  - [ ] 로딩(Loading), 에러(Error), 데이터 없음(Empty State) 처리가 전부 구현되었는가?
  - [ ] 시맨틱 마크업을 지키고 있으며 접근성을 위반한 하드코딩 결함(예: `aria-label` 또는 `alt` 누락 등)이 없는가?
  - [ ] API Mutation 처리 시 `isPending` 속성 등을 활용한 중복 요청 방지 로직과 캐시 무효화 처리가 적용되었는가?
