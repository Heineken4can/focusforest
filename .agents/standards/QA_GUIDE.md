# QA 스탠다드 및 가이드라인 (QA)

이 문서는 웹 서비스의 최종 품질 보증과 테스트 자동화 전략(QA)을 수행하기 위한 가이드라인입니다.

---

## 0. AI 협업 및 프로젝트 특화 원칙 (Core Workflow)

실무 프로젝트 경험을 바탕으로, AI 파트너와 협업 시 아래 원칙을 최우선으로 적용합니다.

- **도메인 권한 엄수 (Cross-Domain Read-Only)**: QA 에이전트(`qa`)는 품질 검증을 위한 작업 폴더(`docs/07. qa/`) 및 테스트 코드/스크립트 내에서만 쓰기/수정 권한을 가집니다. 검증 도중 기획(PO), 백엔드(BE), 프론트엔드(FE)의 기획 문서나 프로덕션 코드를 직접 수정(버그 픽스 등)해서는 절대 안 되며, 발견된 결함은 반드시 `docs/07. qa/결함리포트.md` 형태로 문서화하여 유저에게 해당 파트의 에이전트(예: `fe-act`)를 호출해 수정하도록 명확히 가이드합니다.
- **객관적 독립 검증 (Independent Verification)**: 개발자가 짠 논리나 코드를 맹신하지 않고, 사용자 시나리오 및 예외 상황(Edge Case) 관점에서 철저하게 독립적인 시야로 교차 검증을 수행합니다.
- **명시적 핸드오프 (Handoff)**: QA 단계(Plan ➡️ Act ➡️ Review) 간, 그리고 타 개발 파트로 버그 수정을 이관할 때 명확한 버그 재현 경로와 증빙(스크린샷 등)을 담은 산출물을 건네어 원활한 핑퐁이 이루어지게 합니다.

## 1. 테스트 원칙 및 범위

- **교차 브라우징**: 주요 타겟 브라우저(Chrome, Safari 등) 및 다중 해상도(모바일, 태블릿, 데스크탑)에 걸쳐 동일한 시각적·기능적 경험을 제공하는지 점검합니다.
- **테스트 케이스 커버리지**: Happy Path 중심의 검증뿐만 아니라, 예상치 못한 입력을 가하는 방어적 테스팅(Edge Case)을 필수적으로 수행합니다.
- **이해관계자 분리**: 개발자는 자신이 작성한 코드를 독립적으로 검증하기 어려우므로, QA 에이전트(또는 담당자)가 제 3자의 입장에서 회귀 테스트를 전담합니다.

### 1-1. 테스트 우선순위 분류 기준 (심각도)

| 등급         | 명칭     | 정의                                      | 예시                                                | 대응 기한     |
| ------------ | -------- | ----------------------------------------- | --------------------------------------------------- | ------------- |
| **P0** | Critical | 서비스 전체 장애 또는 핵심 기능 완전 불가 | 로그인 불가, 결제 실패, 데이터 유실, 화이트스크린   | 즉시 (핫픽스) |
| **P1** | Major    | 주요 기능의 부분 장애, 우회 경로 없음     | 특정 조건에서 폼 제출 실패, 필수 페이지 렌더링 깨짐 | 1영업일 이내  |
| **P2** | Minor    | 기능 동작하나 기대와 다름, 우회 가능      | UI 정렬 틀어짐, 오탈자, 비필수 애니메이션 오작동    | 다음 스프린트 |
| **P3** | Trivial  | 사용성에 거의 영향 없음                   | 미세 간격 차이, 콘솔 경고(기능 무관)                | 백로그        |

## 2. 결함(Bug) 리포팅 포맷

이슈가 발견되면 다음의 형식에 맞춰 상세하게 리포트해야 개발자가 빠른 조치를 취할 수 있습니다.

1. **Title**: 직관적인 이슈 요약문
2. **Environment**: 재현된 환경 (브라우저 종류, 해상도, OS 기기)
3. **Pre-conditions**: 이슈 재현을 위한 사전 세팅 조건
4. **Steps to Reproduce**: 버그를 재현하기 위한 구체적이고 순차적인 클릭/입력 단계
5. **Expected Result**: 기획서상 기대되는 정상 결과
6. **Actual Result**: 실제로 나타난 오작동 화면 결과

> 추가로 **Severity**(P0~P3)와 **스크린샷/영상**을 첨부하면 대응 속도가 크게 향상됩니다.

## 3. 효율적 테스트 전략

### 3-1. 테스트 도구 기준

| 테스트 유형           | 권장 도구                         | 용도                                 |
| --------------------- | --------------------------------- | ------------------------------------ |
| **단위 테스트** | Jest / Vitest                     | 개별 함수, 유틸리티, 훅 등 로직 검증 |
| **통합 테스트** | Testing Library (React/Vue)       | 컴포넌트 렌더링 및 상호작용 검증     |
| **E2E 테스트**  | Playwright (1순위) / Cypress      | 실제 유저 시나리오 전체 흐름 검증    |
| **시각 회귀**   | Playwright Screenshot / Chromatic | UI 스냅샷 비교                       |
| **API 테스트**  | Postman / REST Client             | 백엔드 API 응답 검증                 |

### 3-2. E2E 테스트 (browser_subagent 활용)

화면 진입 -> 요소 렌더링 검사 -> 입력 창 상호작용 -> 버튼 클릭 -> 응답결과 확인이라는 실제 유저 시나리오를 자동화 툴 관점으로 시뮬레이션합니다.

### 3-3. 성능 검사

- **육안 검사**: 페이지 렌더링 지연 속도, 큰 이미지 미스로드, 애니메이션 멈춤, 과도한 API 호출 흔적 등을 QA 과정에서 식별합니다.
- **성능 테스트 기준**:

| 지표                           | 목표         | 측정 방법                   |
| ------------------------------ | ------------ | --------------------------- |
| FCP (First Contentful Paint)   | 1.5초 이내   | Lighthouse / Web Vitals     |
| LCP (Largest Contentful Paint) | 2.5초 이내   | Lighthouse / Web Vitals     |
| TTI (Time to Interactive)      | 3.0초 이내   | Lighthouse                  |
| API 응답 시간 (일반)           | 500ms 이내   | 네트워크 탭 / 모니터링 도구 |
| API 응답 시간 (복잡 쿼리)      | 2,000ms 이내 | 네트워크 탭 / 모니터링 도구 |
| CLS (Cumulative Layout Shift)  | 0.1 이하     | Lighthouse / Web Vitals     |

### 3-4. 회귀 테스트 범위 결정 기준

- **Full Regression**: 메이저 릴리즈, 아키텍처 변경, 공통 모듈(인증/권한/라우팅) 수정 시
- **Partial Regression**: 특정 피처 수정 시 해당 피처 + 직접 연관 피처만 회귀
- **Smoke Test**: 핫픽스 배포 시 핵심 Happy Path(로그인, 메인 진입, 핵심 CRUD) 3~5건 빠르게 수행
- 회귀 범위는 변경 영향도 분석(Impact Analysis) 결과를 기반으로 QA-Plan 단계에서 확정합니다.

### 3-5. 보안 테스트 항목 (OWASP Top 10 기반)

QA 수행 시 아래 항목을 체크리스트로 점검합니다. 전문 보안 감사와는 별도입니다.

| 번호 | 항목             | 점검 내용                                                        |
| ---- | ---------------- | ---------------------------------------------------------------- |
| A01  | 접근 제어 취약점 | 비인가 사용자가 타인 데이터 접근 가능한지 URL 직접 입력으로 확인 |
| A02  | 암호화 실패      | 민감 정보(비밀번호, 토큰)가 평문 노출되지 않는지 확인            |
| A03  | 인젝션           | 입력 필드에 `<script>`, SQL 구문 등 삽입 시 필터링 여부 확인   |
| A05  | 보안 설정 오류   | 불필요한 에러 상세 노출, 디버그 모드 활성화 여부 확인            |
| A07  | 인증 실패        | 세션 만료 처리, 로그아웃 후 뒤로가기 접근 차단 여부 확인         |

### 3-6. 결과 아카이빙

검수가 완료된 내역은 `QA_REPORT.md` 형태로 남겨, 개발팀에 통보함으로써 검증 이력을 트래킹합니다. (템플릿은 하단 부록 A 참조)

## 4. 역할별 특별 지침

### 4-1. QA-Plan (테스트 계획)

**책임**: 스프린트/릴리즈 단위의 테스트 계획을 수립합니다.

**테스트 계획서 작성 기준**:

1. 대상 기능 목록을 기획서/PRD에서 추출한다.
2. 각 기능에 대해 테스트 유형(단위/통합/E2E)을 결정한다.
3. 테스트 케이스를 작성하고 우선순위(P0~P3)를 부여한다.
4. 테스트 환경(브라우저, 디바이스, 데이터 셋)을 정의한다.
5. 실행 순서 및 예상 소요 단계를 명시한다.

**테스트 범위 및 우선순위 결정 방법**:

- **In-Scope 결정**: 신규 기능, 변경된 기능, 변경 영향을 받는 연관 기능
- **Out-of-Scope 결정**: 변경 없는 독립 모듈 (단, 메이저 릴리즈 시 Full Regression)
- **우선순위 결정 기준**:

  - 비즈니스 임팩트 (매출/사용자 직결 기능 우선)
  - 사용 빈도 (DAU 기준 상위 시나리오 우선)
  - 변경 규모 (대규모 리팩토링 > 단순 UI 수정)
  - 과거 결함 이력 (결함 빈발 모듈 우선)
- **타 역할 핸드오프(Handoff) 체크리스트**:

  - **to QA-Act**: 테스트 우선순위(P0~P3) 및 테스트 케이스(TC) 리스트, 활용할 테스트 환경/브라우저 스펙 정의서 전달.

### 4-2. QA-Review (검수 및 릴리즈 승인)

**책임**: 테스트 결과를 검토하고 릴리즈 가능 여부를 판단합니다.

**검수 중점 사항 (Review Checklist)**:

- [ ] 도메인 권한 준수: QA 에이전트가 다른 파트(FE, BE 등)의 코드를 무단으로 직접 수정하지 않고 정상적인 에러 리포팅을 수행했는가?
- [ ] 모든 P0/P1 핵심 테스트 케이스가 예외 없이 100% 실행 완료되었는가?
- [ ] 결함(버그) 리포트가 재현 경로(Steps to Reproduce)와 증빙을 포함하여 개발자가 수정 가능한 포맷으로 작성되었는가?
- [ ] 미해결 이슈에 대한 명확한 의사결정(수정 요청 / 보류 / 예외허용)이 완료되었는가?

**릴리즈 승인(Sign-off) 조건**:

| 조건        | 기준                                      | 필수 여부 |
| ----------- | ----------------------------------------- | --------- |
| P0 버그     | **0건** (미해결 없음)               | 필수      |
| P1 버그     | **0건** 또는 명시적 예외 승인 완료  | 필수      |
| P2 버그     | 잔여 허용, 다음 스프린트 백로그 등록 필수 | 권장      |
| TC 실행률   | P0/P1 케이스**100%** 실행 완료      | 필수      |
| TC 통과율   | 전체 케이스**95% 이상** 통과        | 필수      |
| 회귀 테스트 | 범위 내**전건 통과**                | 필수      |
| 성능 기준   | 3-3절 성능 목표 충족                      | 권장      |
| 보안 체크   | 3-5절 항목 전건 점검 완료                 | 권장      |

> P1 버그 예외 승인 시 반드시 사유와 후속 조치 계획을 QA_REPORT.md에 기록합니다.

**승인 절차**:

1. QA-Act로부터 최종 QA_REPORT.md를 전달받는다.
2. Sign-off 조건 표 기준으로 각 항목을 대조 확인한다.
3. 모든 필수 조건 충족 시 "릴리즈 승인" 판정, QA_REPORT.md에 서명한다.
4. 미충족 시 "릴리즈 보류" 판정, 구체적 사유와 재검수 조건을 명시한다.

### 4-3. QA-Act (테스트 수행)

**책임**: QA-Plan에서 수립한 계획에 따라 실제 테스트를 수행하고 결과를 기록합니다.

**테스트 수행 절차**:

1. QA-Plan의 테스트 계획서를 확인하고, 테스트 환경을 셋업한다.
2. 테스트 케이스를 우선순위 순서(P0 -> P1 -> P2 -> P3)로 실행한다.
3. 각 케이스의 결과를 Pass / Fail / Block / Skip으로 기록한다.
4. Fail 발견 시 2절의 버그 리포팅 포맷에 따라 즉시 결함 리포트를 작성한다.
5. 전체 케이스 실행 완료 후 QA_REPORT.md를 작성한다 (부록 A 템플릿 사용).
6. QA-Review에 최종 리포트를 전달하여 검수를 요청하거나, 발견된 결함(.md)들을 타 파트(FE/BE-Act)에 Handoff 하여 수정을 요청한다.

**검수 요청 전 자체 체크리스트 (Done Criteria)**:

- [ ] TC 우선순위에 기반해 모든 P0/P1 케이스를 수행했는가?
- [ ] 결함 발견 시 내가 직접 타 파트 코드를 고치지 않고 리포트(`.md`) 파일로 구별하여 문서를 남겼는가?
- [ ] 하단 '결과 아카이빙 방법'의 명명 규칙과 저장 경로(`docs/07. qa/` 등)를 정확히 준수하여 증빙을 남겼는가?

**결과 아카이빙 방법**:

- QA_REPORT.md 파일명 규칙: `QA_REPORT_[YYYYMMDD]_[대상기능/버전].md`
- 저장 위치: 프로젝트 루트의 `/docs/07. qa/` 디렉토리
- 스크린샷/영상: `/docs/07. qa/evidence/` 디렉토리에 저장, 리포트에서 상대경로로 참조
- 모든 아카이브는 Git 커밋에 포함하여 이력을 관리한다.
