# 데이터베이스 스탠다드 및 가이드라인 (DB)

이 문서는 데이터베이스 설계 및 마이그레이션(DB-Plan, DB-Review, DB-Act)을 위한 성능 튜닝 및 안정성 중심 가이드라인입니다.

---

## 0. AI 협업 및 프로젝트 특화 원칙 (Core Workflow)

실무 프로젝트 경험을 바탕으로, AI 파트너와 협업 시 아래 원칙을 최우선으로 적용합니다.

- **도메인 권한 엄수 (Cross-Domain Read-Only)**: 데이터베이스 에이전트(`db-plan`, `db-rv`, `db-act`)는 DB 전용 작업 폴더(`docs/05. db/`, `db/` 등) 및 스탠다드 로컬 파일(`.agents/standards/DB_GUIDE.md`) 내에서만 쓰기/수정 권한을 가집니다. 백엔드(BE) 문서나 실제 애플리케이션 코드, 기획 문서(`PRD.md`) 등을 수정해야 할 경우, 절대 직접 덮어쓰지 않고 `docs/05. db/` 하위에 수정 제안서 마크다운(.md) 파일을 별도로 작성한 뒤 유저에게 해당 파트의 에이전트를 호출하도록 가이드합니다.
- **아키텍처 선행 원칙 (Architecture/Schema-First)**: 물리적 스키마 쿼리를 작성하기 전, 반드시 정규화/반정규화 논리와 테이블 명세가 담긴 ERD 및 스키마 문서(`db_schema.md`)를 먼저 확정하여 백엔드 파트와 합의해야 합니다.
- **안전한 핸드오프 (Handoff)**: 스키마 설계(Plan)가 끝난 후 구현(Act) 및 타 파트(BE)로 넘어가기 전, 명시적인 Handoff 산출물과 리뷰 과정을 거쳐 데이터 무결성이 보장된 상태로 다음 단계로 이행해야 합니다.

## 1. DBMS 선정 기준

프로젝트 특성에 따라 적합한 DBMS를 선정합니다. 아래 기준을 참고하여 초기 설계 단계에서 결정하고, 결정 근거를 문서에 기록합니다.

| 기준 | SQLite | PostgreSQL | MySQL |
|------|--------|------------|-------|
| **적합 규모** | 프로토타입, 소규모, 임베디드 | 중~대규모, 복잡한 쿼리/데이터 타입 | 중규모, 읽기 중심 워크로드 |
| **동시 접속** | 낮음 (단일 쓰기 잠금) | 높음 (MVCC 기반) | 중~높음 |
| **고급 기능** | 제한적 | JSONB, 배열, CTE, 윈도우 함수 등 풍부 | JSON 지원, 복제 용이 |
| **운영 비용** | 서버 불필요, 파일 기반 | 별도 서버 필요, 관리 복잡도 중간 | 별도 서버 필요, 관리 복잡도 낮음 |
| **권장 시나리오** | MVP/PoC, 로컬 개발, 모바일 앱 | 데이터 정합성 중시, 복잡한 비즈니스 로직 | 웹 서비스, 읽기 비율 높은 서비스 |

- 선정 결과와 근거는 `db_schema.md` 또는 프로젝트 설계 문서에 명시합니다.
- MVP 단계에서 SQLite로 시작하더라도, 이후 마이그레이션을 고려하여 ORM 또는 쿼리빌더를 통한 DBMS 추상화를 권장합니다.

## 2. 스키마 설계 원칙
- **정규화 (Normalization)**: 데이터의 중복을 제거하고 무결성을 보장하기 위해 기본적으로 제3정규형(3NF)을 따릅니다.
- **반정규화 (De-normalization)**: 조인 비용이 매우 높아 조회 성능 저하가 극대화되는 것이 확인된 지표가 있을 경우에만 제한적으로 컬럼을 중복시켜 반정규화를 허용합니다.
- **명명 규칙 (Naming)**: 테이블명과 컬럼명은 snake_case를 사용하며, 예약어 사용을 금지합니다. boolean 타입 컬럼명은 `is_` 또는 `has_`를 포함시킵니다.
- **감사 로그 (Audit Log) 테이블**: 주요 엔티티의 변경 이력을 추적해야 하는 경우, 별도의 감사 로그 테이블을 설계합니다. 최소 포함 컬럼은 아래와 같습니다.
  - `id`, `table_name`, `record_id`, `action` (INSERT/UPDATE/DELETE), `changed_fields` (JSON), `old_values` (JSON), `new_values` (JSON), `performed_by`, `performed_at`
  - 감사 로그 테이블은 INSERT 전용으로 설계하며, 수정/삭제를 금지합니다.

## 3. 성능 및 쿼리 최적화
- **인덱스 전략**: 카디널리티(Cardinality)가 높고 `WHERE`, `JOIN`, `ORDER BY`에 자주 사용되는 컬럼에 대해 단일/복합 인덱스를 구성합니다. 단, 쓰기 빈도가 잦은 테이블에 대한 무분별한 인덱스 생성은 피합니다.
- **N+1 문제 회피**: ORM 환경을 사용하는 경우 `Fetch Join`이나 `Batch Size` 튜닝을 통해 불필요하게 많은 단일 쿼리가 발생하는 것을 사전에 차단합니다.
- **페이징 쿼리**: 데이터 수가 방대할 우려가 있는 경우, `OFFSET`을 사용하는 전통적 페이징 대신 성능 저하를 방지할 수 있는 커서 기반 페이징(Cursor-based Pagination) 설계를 우선합니다.

## 4. 마이그레이션
- **마이그레이션 스크립트**: DB 스키마 수정 시 반드시 롤백(Rollback) 쿼리를 함께 작성하여 장애 상황에 즉각 복구할 수 있는 무중단 배포를 목표로 합니다.
- **버전 관리**: 마이그레이션 파일은 타임스탬프 또는 순번 기반으로 버전을 관리하며, 한 번 적용된 마이그레이션은 수정하지 않고 새 마이그레이션으로 변경사항을 반영합니다.
- **시드(Seed) 데이터 관리**: 개발/테스트 환경에서 필요한 초기 데이터는 시드 스크립트로 분리하여 관리합니다.
  - 시드 데이터는 마이그레이션 스크립트와 별도 디렉터리에 보관합니다.
  - 환경별(dev/staging/prod) 시드 데이터를 구분하며, 프로덕션 시드는 코드 마스터 등 필수 레퍼런스 데이터만 포함합니다.
  - 시드 스크립트는 멱등성(idempotent)을 보장하여 중복 실행 시에도 안전해야 합니다.


---

## 5. 데이터 무결성 및 안정성
- **Soft Delete 의사결정 기준**: 기본적으로 중요한 데이터의 물리적 삭제(`DELETE`)보다는 `deleted_at` 등의 컬럼을 추가해 논리적 삭제 처리를 권장합니다. 단, 아래 조건에 해당하는 경우 Hard Delete를 허용합니다.
  - **법적 삭제 의무**: GDPR의 "잊혀질 권리(Right to Erasure)", 개인정보보호법 등 법령에 의해 물리적 삭제가 요구되는 경우
  - **민감 개인정보**: 사용자가 계정 탈퇴를 요청하고, 보유 기간이 만료된 개인식별정보(PII)
  - **임시/휘발성 데이터**: 세션, 임시 토큰, 캐시성 데이터 등 보존 가치가 없는 데이터
  - Hard Delete 적용 시 반드시 삭제 전 백업 또는 감사 로그 기록을 선행하고, 해당 정책을 설계 문서에 명시합니다.
- **트랜잭션 (ACID)**: 데이터 일관성이 절대적으로 유지되어야 하는 부분(결제, 재고 증감 등)에서는 Lock 기법 등 적절한 트랜잭션 레벨 통제가 이루어져야 합니다.
- **참조 무결성**: 외래 키 제약조건을 적극 활용하여 고아 레코드(orphan record) 발생을 방지합니다. Soft Delete 테이블 간 참조 시에는 조회 쿼리에서 `deleted_at IS NULL` 조건을 누락하지 않도록 유의합니다.

## 6. 데이터 보안
- **민감정보 암호화**: 비밀번호는 반드시 단방향 해시(bcrypt, argon2 등)로 저장합니다. 주민등록번호, 카드번호 등 복호화가 필요한 민감정보는 AES-256 이상의 대칭키 암호화를 적용하며, 암호화 키는 애플리케이션 코드와 분리하여 환경변수 또는 별도 키 관리 시스템(KMS)에서 관리합니다.
- **데이터 마스킹**: 로그, 관리자 화면, API 응답 등에서 민감정보(이메일, 전화번호, 주소 등)는 부분 마스킹 처리하여 노출합니다. (예: `010-****-1234`, `u***@example.com`)
- **접근 제어**: DB 접속 계정은 역할별(읽기 전용, 읽기/쓰기, 관리자)로 분리하고, 최소 권한 원칙(Principle of Least Privilege)을 적용합니다. 프로덕션 DB에 대한 직접 접근은 제한합니다.

## 7. 백업 및 복구 전략

- **백업 주기**:
  - 프로덕션 환경: 일 1회 이상 전체 백업(Full Backup), 변경분은 시간 단위 증분 백업(Incremental Backup) 권장
  - 스테이징/개발 환경: 주 1회 이상 전체 백업
- **백업 보관 기간**: 최소 30일간 보관하며, 법적 요건이 있는 경우 해당 기간에 맞춰 보관 기간을 조정합니다.
- **복구 절차**:
  - 복구 목표 시점(RPO, Recovery Point Objective)과 복구 목표 시간(RTO, Recovery Time Objective)을 사전에 정의합니다.
  - 분기 1회 이상 복구 테스트(Disaster Recovery Drill)를 수행하여 실제 복구 가능 여부를 검증합니다.
- **백업 검증**: 백업 파일의 무결성을 주기적으로 검증하며, 백업 실패 시 알림이 발송되도록 모니터링을 구성합니다.

## 8. 역할별 특별 지침

### DB-Plan (설계자) 특별 지침
- ERD 설계 시 정규화 원칙을 우선하되, 성능상의 명확한 근거 기반이 있는 경우에 한하여 반정규화를 설계에 반영합니다.
- 각 테이블의 특성과 예상 트래픽을 고려하여 효과적인 초기 인덱스(Index) 전략을 함께 명시합니다.
- **필수 산출물**: DB-Plan 단계에서 아래 산출물을 반드시 작성하고, 후속 단계(Review/Act)에 인계합니다.
  - **ERD (Entity-Relationship Diagram)**: 테이블 간 관계, 카디널리티, PK/FK를 시각적으로 표현한 다이어그램. Mermaid 또는 dbdiagram.io 형식 권장.
  - **db_schema.md**: 아래 항목을 포함하는 스키마 정의 문서
    - DBMS 선정 결과 및 근거
    - 전체 테이블 목록 및 각 테이블의 역할 설명
    - 컬럼 정의 (컬럼명, 타입, 제약조건, 기본값, 설명)
    - 인덱스 전략 (대상 컬럼, 인덱스 타입, 근거)
    - Soft Delete / Hard Delete 정책 (테이블별 적용 기준)
    - 감사 로그 대상 테이블 및 추적 범위
- **타 역할 핸드오프(Handoff) 체크리스트**:
    - **to BE-Plan / BE-Act**: 백엔드 애플리케이션 연동을 위한 최종 ERD, 스키마 명세 문서(`.md`), 특수 인덱스 최적화 전략 설명.
    - **to DB-Act**: ERD 명세가 완벽히 반영되어 실제 DDL 스크립트로 번역 가능한 수준의 `db_schema.md` 문서 완성.

### DB-Review (검수자) 특별 지침
- 테이블 간 참조 무결성 제약조건(FK 등)이 올바르게 설계되었는지 꼼꼼하게 점검합니다.
- 테이블 변경 시 일어날 수 있는 데이터 유실 한계점을 검토하고, 문서나 코드는 절대 수정하지 않은 채 리포팅합니다.
- **검수 중점 사항 (Review Checklist)**:
    - [ ] DB 도메인 전용 폴더(`docs/05. db/`) 외부의 백엔드/프론트엔드/기획 문서를 무단으로 침범·수정하지 않았는가? (도메인 권한 준수)
    - [ ] 정규화 원칙(3NF)이 준수되었으며, 반정규화가 적용된 경우 성능 향상의 논리적 근거가 타당한가?
    - [ ] 인덱스가 조인(JOIN) 및 검색 조건(WHERE)에 맞게 적절히 설계되었으며, N+1 쿼리 등의 성능 병목 우려가 없는가?
    - [ ] 소프트 딜리트(Soft Delete) 적용 및 데이터 암호화(보안) 기준이 정확히 반영되었는가?


### DB-Act (실행자) 특별 지침
- 마이그레이션 스크립트를 작성할 때 돌발 상황을 방지하기 위해 '반드시' 롤백(Rollback) 쿼리를 함께 작성합니다.
- 실제 데이터베이스 쿼리를 성능 튜닝 가이드에 맞춰 병목 없이 실행되도록 최적화합니다.
- **검수 요청 전 자체 체크리스트 (Done Criteria)**:
    - [ ] 마이그레이션 스크립트에 생성(UP) 쿼리와 함께 롤백(DOWN) 쿼리 로직이 누락 없이 작성되었는가?
    - [ ] 인덱스 생성 스크립트가 설계 문서에 맞춰 정확히 포함되었는가?
    - [ ] 테스트/개발 환경 구축을 위해 필요한 최소한의 시드(Seed) 데이터 스크립트가 준비되었는가?
