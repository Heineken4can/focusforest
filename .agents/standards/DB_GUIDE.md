# 데이터베이스 스탠다드 및 가이드라인 (DB)

이 문서는 데이터베이스 설계, 구현, 리뷰, 핸드오프 전 과정에서 공통으로 따르는 단일 원본입니다.
`db-plan`, `db-rv`, `db-act`는 모두 이 문서를 기준으로 판단하며, 스킬 문서는 이 기준을 작업에 적용하는 보조 수단으로만 사용합니다.

---

## 0. 문서 목적과 적용 범위

- 적용 대상: `docs/05. db/`, Prisma 스키마, 마이그레이션, seed, DB 운영 관련 설정
- 적용 단계: 설계(`db-plan`), 리뷰(`db-rv`), 구현(`db-act`)
- 우선순위: 본 문서 > 스킬 문서 > 임시 작업 메모
- 목표: 스키마 설계 기준, 구현 기본값, 리뷰 체크포인트, 완료 조건을 한 문서에서 제공

---

## 1. AI 협업 및 프로젝트 특화 원칙

- **도메인 권한 엄수**: DB 에이전트는 `docs/05. db/`, DB 관련 코드, `.agents/standards/DB_GUIDE.md` 범위에서만 직접 수정합니다.
- **크로스 도메인 읽기 전용**: BE, FE, UI, PO 문서는 읽기만 가능하며 변경이 필요하면 제안서로 남깁니다.
- **Schema-First**: 물리 스키마나 마이그레이션 전에 ERD, 관계, 삭제 정책, 인덱스 전략을 먼저 확정합니다.
- **무결성 우선**: 편의상 애플리케이션 레이어에 맡기기보다 DB 차원에서 제약을 표현하는 쪽을 우선합니다.
- **안전한 핸드오프**: 스키마 변경 배경, 영향 범위, 롤아웃 순서, 롤백 가능성을 함께 전달합니다.

---

## 2. 설계 원칙

### 2.1 엔터티와 관계 설계

- 기본적으로 제3정규형(3NF)을 따릅니다.
- 반정규화는 측정된 성능 병목이 있고 근거가 문서에 남을 때만 허용합니다.
- 참조 무결성이 필요한 관계에는 FK 또는 동등한 제약을 둡니다.
- 삭제 정책(`restrict`, `cascade`, `set null`, soft delete`)은 관계마다 명시합니다.

### 2.2 DBMS 선정 기준

- MVP 또는 로컬 중심이면 SQLite를 검토할 수 있습니다.
- 정합성과 복잡한 쿼리가 중요하면 PostgreSQL을 우선 검토합니다.
- 읽기 중심 웹 서비스는 MySQL도 선택 가능합니다.
- 선정 결과와 근거는 DB 설계 문서에 명시합니다.

### 2.3 무결성과 보존 정책

- 중요한 데이터는 기본적으로 soft delete를 우선 검토합니다.
- 법적 삭제 의무나 휘발성 데이터는 hard delete를 허용합니다.
- 금액, 수량, 상태값 같은 핵심 비즈니스 규칙은 가능한 한 DB 제약으로 표현합니다.

---

## 3. 구현 컨벤션

### 3.1 Prisma 스키마 구조 규칙

- 모델명은 `PascalCase` 단수형을 사용합니다.
- 필드명은 `camelCase`를 사용합니다.
- 실제 테이블 또는 컬럼명이 snake_case라면 `@@map`, `@map`으로 매핑합니다.
- 관계 필드명은 단수 또는 복수 규칙을 일관되게 유지합니다.

### 3.2 nullable / default / unique 기준

- nullable은 진짜 선택값에만 허용합니다.
- 생성/수정 시각은 기본값과 자동 갱신 규칙을 명시합니다.
- 비즈니스 유일성 규칙은 애플리케이션 로직이 아니라 DB 제약으로 먼저 표현합니다.
- 단순 편의상 nullable을 늘리거나 unique를 생략하지 않습니다.

### 3.3 인덱스 기준

- `WHERE`, `JOIN`, `ORDER BY`에 자주 쓰이는 컬럼을 기준으로 인덱스를 설계합니다.
- 복합 인덱스는 선택도와 조회 패턴 순서를 반영합니다.
- 쓰기 비용만 높이는 과잉 인덱스는 피합니다.
- soft delete 패턴이 많다면 그 조회 조건을 고려한 인덱스를 검토합니다.

### 3.4 migration 규칙

- 한 번 적용된 migration은 수정하지 않고 새 migration으로 변경사항을 반영합니다.
- 파괴적 변경은 기존 데이터 처리 전략, 배포 순서, 롤백 가능성을 함께 문서화합니다.
- 대용량 테이블 변경은 락 영향과 무중단 가능성을 먼저 검토합니다.
- 마이그레이션은 가능한 한 재실행 안전하게 작성합니다.

### 3.5 seed 규칙

- seed는 migration과 분리합니다.
- 개발, 테스트, 운영 환경의 seed 범위를 구분합니다.
- 운영 seed는 필수 레퍼런스 데이터만 포함합니다.
- seed는 중복 실행해도 안전해야 합니다.

### 3.6 쿼리 규칙

- 쿼리 레이어에서 `include`와 `select`를 목적에 맞게 최소화합니다.
- 기본값으로 모든 관계와 필드를 끌고 오지 않습니다.
- 대량 목록은 cursor 기반 pagination을 우선 검토합니다.
- 실시간 집계가 비싸면 사전 계산 테이블이나 집계 전략을 설계 단계에서 정의합니다.

### 3.7 보안 및 운영 규칙

- 비밀번호는 단방향 해시로 저장합니다.
- 복호화가 필요한 민감정보는 애플리케이션 코드와 분리된 키 관리 전략을 사용합니다.
- DB 계정은 최소 권한 원칙으로 분리합니다.
- 백업 주기, 보관 기간, 복구 테스트 주기를 운영 문서에 명시합니다.

---

## 4. 테스트 및 검증 기준

- migration은 빈 데이터셋과 기존 데이터셋 관점에서 모두 검토합니다.
- destructive change는 적용 전후 영향과 롤백 경로를 검증합니다.
- seed는 중복 실행 안정성을 확인합니다.
- 성능상 중요한 조회는 인덱스와 실행 계획을 함께 확인합니다.

---

## 5. 리뷰 체크포인트

### 5.1 스키마 정확성

- 타입, nullable, default, unique, FK가 비즈니스 규칙과 일치하는가

### 5.2 인덱스 전략

- 조회 패턴과 인덱스 설계가 맞는가
- 과잉 또는 누락 인덱스가 없는가

### 5.3 마이그레이션 안전성

- 파괴적 변경, 락 위험, 순서 의존, 롤백 불가 이슈가 없는가

### 5.4 데이터 무결성

- soft delete, 상태값, 중복 방지, 고아 레코드 처리가 충분한가

### 5.5 Prisma 관례

- 모델/필드/관계 네이밍과 `@map` 또는 `@@map` 사용이 일관적인가
- 쿼리 레이어에서 `include`나 `select` 남용이 없는가

### 5.6 성능 고려

- pagination, 집계, JSON 컬럼 사용, connection 설정이 타당한가

---

## 6. Done Criteria

- 스키마 변경 이유와 영향 범위가 문서화되어 있다.
- migration과 seed가 역할별로 분리되어 있다.
- 파괴적 변경의 대응 전략이 정리되어 있다.
- 인덱스와 무결성 제약이 설계 의도와 일치한다.
- 필요한 경우 백엔드와 연동 계약이 함께 갱신되었다.

---

## 7. Handoff 기준

### 7.1 to DB-Review

- 변경 대상 모델 또는 테이블 요약
- 데이터 유실 및 락 리스크
- migration 또는 seed 검증 결과

### 7.2 to BE

- 최종 스키마와 관계 정의
- nullable, default, 삭제 정책
- 쿼리 또는 인덱스 사용 시 주의점

---

## 8. 역할별 특별 지침

### DB-Plan

- ERD, 컬럼 정의, 인덱스, 삭제 정책, 감사 로그 전략을 먼저 확정합니다.
- DBMS 선택 근거와 반정규화 근거를 남깁니다.

### DB-Review

- 문서나 코드 직접 수정 없이 무결성, 성능, 안전성 중심으로 findings를 남깁니다.
- 크로스 도메인 영향이 있으면 관련 파트로 핸드오프 포인트를 명시합니다.

### DB-Act

- migration을 안전하게 작성하고, destructive change는 배포/롤백 전략과 함께 다룹니다.
- seed, 인덱스, 제약 조건이 설계 문서와 맞는지 직접 검증합니다.
