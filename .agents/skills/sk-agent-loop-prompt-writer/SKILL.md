# 반복형 에이전트 프롬프트 작성 스킬

## 개요

이 스킬은 현재 대화와 최신 리뷰 결과를 바탕으로,
이 저장소 전용 서브에이전트 실행 프롬프트를 조립합니다.

출력 목표는 설명이 아니라 바로 붙여 넣어 실행할 수 있는 프롬프트 세트입니다.

---

## 사용하는 시점

다음과 같은 요청에 이 스킬을 사용합니다.

- "BE 루프용 최종 프롬프트 세트 작성해줘"
- "지금 리뷰 결과 반영해서 UI 수정 프롬프트 만들어줘"
- "db-plan -> db-rv 반복용 프롬프트 정리해줘"
- "지금 대화를 바탕으로 서브에이전트 프롬프트를 만들어줘"

기본 출력 단위는 아래 셋 중 하나입니다.

1. 단일 프롬프트
2. 1개 도메인용 루프 세트
3. BE/DB/UI 다중 도메인 루프 세트

---

## 실행 절차

### STEP 1: 대상 루프 식별

먼저 어떤 도메인의 프롬프트가 필요한지 확정합니다.

- BE: `be-plan`, `be-rv`
- DB: `db-plan`, `db-rv`
- UI: `ui-plan`, `ui-rv`

다음으로 어느 라운드인지 분류합니다.

- 초안 작성
- 1차 리뷰
- 리뷰 반영
- 재리뷰
- 마감 정리

사용자가 명시하지 않으면 최근 대화 흐름을 기준으로 가장 자연스러운 다음 라운드를 가정합니다.

### STEP 2: 저장소 로컬 규칙 반영

프롬프트에는 반드시 이 저장소의 쓰기 스코프를 반영합니다.

- `be-plan`: `docs/03. architecture/architecture.md`, `docs/04. be/*`
- `be-rv`: 원본 문서 수정 금지, 채팅 또는 BE 리뷰 문서만
- `db-plan`: `docs/05. db/*`
- `db-rv`: 원본 문서 수정 금지, 채팅 또는 DB 리뷰 문서만
- `ui-plan`: `docs/02. ui/*`
- `ui-rv`: 원본 문서 수정 금지, 채팅 또는 UI 리뷰 문서만

크로스 도메인 문서는 항상 읽기 전용으로 명시합니다.

### STEP 3: 최소 스킬 조합 선택

기본 조합은 아래를 우선 사용합니다.

- 설계 반영 / 수정 라운드: `$sk-contract-propagation`
- 정합성 리뷰 라운드: `$sk-cross-doc-consistency-review`
- 문서 마감 정리: `$sk-doc-normalizer-ko`

여러 스킬이 동시에 맞더라도 최소 조합만 사용합니다.

### STEP 4: 프롬프트 조립

각 프롬프트에는 아래 항목을 포함합니다.

1. 사용할 서브에이전트
2. 사용할 스킬
3. 수정 가능 범위
4. 읽기 전용 참조 문서
5. 이번 라운드의 목표
6. 반드시 처리할 항목 목록
7. 출력 형식
8. 범위 확장 금지 여부

리뷰 결과가 이미 주어졌다면, 다음 수정 라운드 프롬프트는 반드시 아래 규칙을 넣습니다.

- `CRITICAL`과 `WARN`만 처리
- 새로운 범위 확장 금지
- 반영 여부 표 출력
- 수정 후 regression 자가 점검

### STEP 5: 종료 조건 명시

루프 세트를 출력할 때는 종료 조건도 함께 씁니다.

- `CRITICAL = 0`
- `WARN = 0`
- 남은 항목이 `INFO` 또는 후속 범위 메모만 남음

---

## 프롬프트 구성 규칙

### 1. 도메인별 기본 골격

#### BE 루프

- 초안/수정: `be-plan + $sk-contract-propagation`
- 리뷰: `be-rv + $sk-cross-doc-consistency-review`
- 마감: `be-plan + $sk-doc-normalizer-ko`

#### DB 루프

- 초안/수정: `db-plan + $sk-contract-propagation`
- 리뷰: `db-rv + $sk-cross-doc-consistency-review`
- 마감: `db-plan + $sk-doc-normalizer-ko`

#### UI 루프

- 초안/수정: `ui-plan + $sk-contract-propagation`
- 리뷰: `ui-rv + $sk-cross-doc-consistency-review`
- 마감: `ui-plan + $sk-doc-normalizer-ko`

### 2. 리뷰 프롬프트 규칙

리뷰 프롬프트에는 반드시 아래를 넣습니다.

- findings first
- `CRITICAL`, `WARN`, `INFO` 순
- 파일 경로와 라인 근거 포함
- 수정 없이 리뷰만 수행
- 이슈가 없으면 `PASS` 명시

### 3. 수정 프롬프트 규칙

수정 프롬프트에는 반드시 아래를 넣습니다.

- 직전 리뷰 findings만 반영
- 새로운 정책 추가 금지
- 수정 가능 범위 재명시
- 반영 완료/보류 표 출력

### 4. UI stale TBD 정리 규칙

UI 문서에 확정된 항목이 아직 `미정 / 추가 정의 필요`로 남아 있다면,
새 설계를 만들지 말고 이미 확정된 BE/architecture 계약으로 치환하는 프롬프트를 생성합니다.

대표 항목 예시:

- `startFocusSession` 응답 범위
- `bootstrap` 응답 범위
- `409 conflict` schema
- KPI dedupe 기준
- timezone 재집계 범위

### 5. 현재 대화 기반 우선순위 규칙

사용자가 별도 우선순위를 주지 않으면 아래 순서를 기본값으로 사용합니다.

1. BE 계약 잠금
2. BE 리뷰
3. BE 리뷰 반영
4. BE 재리뷰
5. UI stale TBD 반영 및 리뷰
6. DB 반영 및 리뷰

---

## 출력 형식

출력은 짧은 서문 뒤에 바로 프롬프트 블록을 제공합니다.

권장 형식:

~~~markdown
**BE 루프용**

**1. BE 초안 작성**
~~~text
[실행 프롬프트]
~~~

**2. BE 리뷰**
~~~text
[실행 프롬프트]
~~~
~~~

설명은 최소화하고, 프롬프트가 바로 실행 가능해야 합니다.

---

## 주의사항

- 이 스킬은 프롬프트를 생성하지, 실제 서브에이전트 작업을 대신 수행하지 않습니다.
- 저장소 로컬 규칙과 충돌하는 범위 확장을 제안하지 않습니다.
- 사용자가 제공한 리뷰 findings가 있으면 그것을 최우선 입력으로 사용합니다.
- 동일한 프롬프트를 길게 반복하지 말고, 라운드별 목적이 달라지도록 조립합니다.
